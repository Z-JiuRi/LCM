# BS/UE 端网协同的无线 AI/ML 生命周期候选方案

> **文档状态：用例级候选设计，尚未实现或验证。** 本文早期以 BS/UE 双 Agent 协同为主线展开，不代表项目已经决定采用双 Agent，也不代表本仓库已有相应实现。双侧组件的职责划分、状态机、协议和实现路线均为待比较的方案。
>
> 项目当前研究定位、候选架构和证据要求以[相关论文综述与研究定位](../分析/LCMAgent相关论文综述与研究定位.md)及[LCMAgent 架构设计草案](LCMAgent架构设计草案.md)为准。本文保留双侧协同作为一种候选用例；是否需要 UE 自主 Agent，应由本地信息、权限边界和实验收益决定。标准资料不规定 LLM 或双 Agent 实现。

## 1. 文档定位

本文档研究在 UE 侧和 BS/gNB 侧分别部署控制组件后，如何完成 AI/ML 模型的评估、准备、共同生效、运行监测、切换和回退。

需要先明确来源边界：三份标准资料支持的是 AI/ML 评估、生命周期、数据收集、模型位置和协作约束，并没有规定“BS Agent + UE Agent”的实现，也没有规定 LLM 必须参与。双 Agent 是本文针对这些约束提出的研究架构；在任何具体用例中，双侧模型都只是受控实验对象，不应被表述为标准的优先部署结论。

若实验选择双侧协同，一个待评估的候选方案是不对称地划分网络侧规划与 UE 本地验证职责：

- **BS/gNB 侧**：部署具有全局规划、跨 UE 协调和生命周期编排能力的主 Agent。
- **UE 侧**：部署轻量级本地 Agent Runtime，负责本地状态确认、隐私与资源约束、本地验证和快速回退。
- **两侧之间**：通过结构化的模型生命周期协议协同，而不是通过自然语言自由协商。
- **实时控制层**：由传统算法、专用小模型或确定性控制器完成，不等待 LLM API 返回。

本文档梳理该候选方案的研究问题、系统边界、协同协议、评估方法和可能的实现路线。文中使用的“标准支持”只表示问题边界和约束，具体的双 Agent 架构、证据对象、事务状态机和实验方案均属于项目设计提案，不是标准规定或当前实现。

## 2. 核心结论

### 2.1 是否应该 BS 和 UE 分别配置 Agent

对于以下场景，BS 与 UE 分别配置控制组件是合理的；是否必须拆成两侧组件，要由本地信息、权限和资源边界决定：

- UE 侧模型；
- 双侧模型；
- UE 与网络之间存在模型配对关系；
- UE 本地数据不能完全上传；
- 模型激活需要考虑 UE 本地内存、算力、功耗或版本状态；
- 模型切换需要两端共同生效；
- 需要跨小区保持 UE 侧模型功能连续性。

但“分别配置 Agent”不等于“分别部署完整 LLM”。推荐方案是：

```text
BS/gNB：可部署完整 LLM Agent + 生命周期编排器
UE：轻量 Agent Runtime + 本地确定性验证器
两侧：结构化协同协议 + 共享事务状态
底层：独立的实时无线控制器和回退控制器
```

### 2.2 为什么不采用两个相同的 LLM

BS 与 UE 的资源、信息和职责并不对称：

| 维度 | BS/gNB | UE |
|---|---|---|
| 计算与存储 | 通常较充足 | 受设备和能耗约束 |
| 可见信息 | 多 UE、多小区、网络全局状态 | 本地信号、设备状态和本地数据 |
| 决策范围 | 全局模型选择和跨 UE 协调 | 本地可运行性和本地数据策略 |
| 时延约束 | 可承担慢速管理任务 | 仍需保护本地快速回退和实时控制 |
| 信任边界 | 不能越过 UE 隐私和能力约束 | 不能修改网络全局策略 |
| 主要目标 | 全局收益和生命周期协调 | 本地安全、可运行、低开销 |

相同的 LLM 会导致权限过大、重复推理、状态不一致和资源浪费。双 Agent 的关键不是复制两个 LLM，而是将全局规划与本地事实确认分离。

### 2.3 推荐的研究对象

建议将以下问题作为通用研究对象：

> 面向 UE 侧、网络侧或双侧的 AI/ML 功能，在场景变化、设备异构和证据不完整时，由 BS 主 Agent 与 UE 轻量 Agent 协同完成模型评估、准备、激活、监测、切换和回退。

CSI 压缩或 CSI 预测只是一个便于说明的用例，不是本文固定的锚点。其他具有明确输入输出契约、可测量 KPI、部署约束和回退路径的无线 AI/ML 用例同样适用，例如低开销 DMRS、波束管理、定位增强或其他 UE/网络协作功能。具体选择哪个用例，应由数据可得性、模型位置、评估成本和标准化价值共同决定。

以 CSI 为例，它具备：

- 模型输入输出契约；
- UE 侧、网络侧和双侧模型位置；
- CSI 反馈开销；
- 模型精度、链路性能和系统吞吐量之间的权衡；
- 两端模型配对问题；
- 跨场景泛化问题；
- UE 与网络侧数据收集问题；
- 模型切换和回退需求。

对于 CSI 预测，相关研究讨论提出优先考虑单侧模型。这说明模型位置必须作为用例条件显式配置，而不能默认所有问题都采用双侧模型。本文因此保留单侧模型作为强基线，把双侧模型作为需要额外证明兼容性、协作成本和端到端收益的实验分支。若双 Agent 相比单 Agent 没有降低错误发布、切换失败或本地资源超预算，就应收缩为单侧模型评估与发布系统。

## 3. 标准讨论的映射

R1-2508811 第三章包含三个相互关联的主题：评估与 KPI、LCM 框架、数据收集框架。BS/UE 双 Agent 设计应当把三者串成一个闭环。

```text
数据收集
    ↓
模型训练/适配
    ↓
多层 KPI 评估
    ↓
模型生命周期决策
    ↓
部署、监测、切换或回退
    ↓
新的运行数据和评估证据
```

### 3.1 评估与 KPI

双 Agent 不应只报告模型层精度，还需要共同支持以下指标层级：

| 层级 | BS 侧可观测指标 | UE 侧可观测指标 | 典型用途 |
|---|---|---|---|
| 模型层 | 聚合预测误差、跨 UE 分布 | 本地预测误差、输入有效性 | 判断模型质量 |
| 链路层 | BLER、吞吐量、反馈性能 | 本地解码、推理失败 | 判断无线链路影响 |
| 系统层 | 小区吞吐量、用户公平性、资源利用率 | 设备业务体验、能耗 | 判断最终收益 |
| 运行层 | 模型切换成本、统计退化 | 推理时延、内存、功耗 | 判断能否部署 |
| 生命周期层 | 发布成功率、回退率、跨 UE 一致性 | 本地拒绝率、模型状态 | 判断管理质量 |

第三章讨论的关键原则在双 Agent 中体现为：

- 中间模型指标不能替代链路和系统指标；
- 系统指标也不能完全解释模型为什么失效；
- 推理、性能监测、训练、微调、数据收集和切换开销必须计入；
- 泛化性能应针对明确的场景变化定义；
- 训练时延、功耗和模型存储等指标应按用例和部署位置选择性评估。

### 3.2 生命周期管理

双 Agent 需要支持的不只是模型下载，而是完整的生命周期：

```text
注册
→ 能力匹配
→ 适用性评估
→ 准备
→ 本地验证
→ 共同生效
→ 运行监测
→ 继续运行 / 微调 / 切换 / 回退
→ 退役
```

其中，BS Agent 负责全局流程编排，UE Agent 负责本地状态确认和本地安全门。两端必须保留独立的回退能力。

### 3.3 数据收集

数据收集需要明确：

- 数据是什么；
- 从 UE、BS 还是两端采集；
- 用于训练、验证、测试还是运行监测；
- 标签来自理想信道、传统估计器、实际业务结果还是自监督信号；
- 数据对应哪个模型版本、配置和场景；
- 是否允许上传；
- 采集的计算、存储、空口和能耗成本是多少。

UE Agent 的主要价值是本地数据治理和隐私控制，BS Agent 的主要价值是全局数据需求规划、跨 UE 统计和评估任务编排。

### 3.4 设计取舍与适用范围

本文将模型生命周期、CSI 端到端评估、证据驱动补测、数据最小化和隐私安全门统一到同一套双侧协同框架中，但只保留能够直接服务于模型评估与生命周期管理的内容。

| 内容 | 本文处理方式 | 设计边界 |
|---|---|---|
| 多层 KPI、复杂度/时延/存储/功耗、泛化、厂商协作 | 作为通用评估要求 | 不能只用单一模型精度证明可部署 |
| Model ID 与 Functionality 两种管理视角 | 作为模型注册和检索方式 | 功能相同不代表实现天然兼容 |
| 模型交付、选择、激活、停用、切换、回退、监测和更新 | 作为 LCM 状态机和事务流程 | LLM 只能规划，不能绕过验证器和执行门 |
| CSI 估计—压缩—反馈—重建—系统 KPI | 作为一个具体用例的评估链路 | 不限制其他用例采用相同链路 |
| UE/BS 数据职责、数据血缘、采集成本、本地权限门 | 作为所有用例的基本数据治理要求 | 数据请求必须按用途和最小必要范围提出 |
| 联邦学习、差分隐私、隐私预算、参与者选择 | 保留为可插拔的后续扩展 | 不纳入第一版闭环，也不假设标准已经规定 |
| 具体工具 API、固定候选模型名称和统一模型市场 | 不作为架构前提 | 实现时可替换，不能写成标准要求 |

### 3.5 标准约束的统一解释

三份标准资料在本文中被统一转化为以下设计约束：

1. 评估必须同时覆盖模型层、链路层、系统层和运行成本，不能只看准确率或重构误差。
2. 生命周期必须处理模型标识、适用条件、训练/微调、交付、激活、监测、切换、回退和退役。
3. 模型位置可以是 UE 侧、网络侧或双侧；模型位置变化会改变数据、资源、协作和切换要求。
4. 数据收集必须明确内容、格式、来源、标签、用途、质量、时延、隐私和采集成本。
5. UE 与网络之间的协作可以分层，但不能把研究中的 Agent 组件直接当作标准协议实体。
6. 隐私、可信、韧性和能耗是系统约束，不应被当作模型上线后的附加说明。

本文据此构造独立的 BS/UE 双侧协同架构；标准只提供问题边界和约束，本文负责给出可执行的 Agent 分工、验证流程和实验方案。

## 4. 目标与非目标

### 4.1 研究目标

研究一个能够在有限评估和部署预算下完成以下任务的双 Agent 系统：

1. 从模型说明、设备能力、运行报告和测试记录中提取可验证的发布条件。
2. 识别当前模型的证据缺口和适用性缺口。
3. 规划最有价值的补测和数据收集任务。
4. 判断继续运行、网络侧适配、UE 侧适配、双侧更新、模型切换和传统回退之间的成本收益。
5. 在两端模型兼容并且本地约束满足时完成共同准备和共同生效。
6. 在部署后持续监测模型性能和适用条件。
7. 在模型退化、版本不一致或一端失效时进行安全回退。

### 4.2 非目标

第一阶段不研究：

- 让 LLM 直接控制每个时隙的调度、HARQ 或快速功控；
- 让 LLM 直接生成和发布未经验证的模型权重；
- 让 UE 与 BS 通过自然语言自由协商协议；
- 同时覆盖所有 AI/ML 空口用例；
- 用 Agent 替代底层无线仿真器、兼容性检查器和安全执行门；
- 让 Agent 修改自己的权限、验证器或安全策略；
- 把研究讨论中的 LCM 提案直接描述为已经标准化的协议流程。

## 5. 系统模型

### 5.1 实体

系统包含以下实体：

```text
BS/gNB Agent
    负责全局规划、生命周期编排和跨 UE 协调

UE Agent Runtime
    负责本地约束、数据治理、验证和回退

Model Registry
    保存模型卡、版本、适用条件、配对关系和证据引用

Evaluation Engine
    执行链路级、系统级、模型级和资源级评估

Compatibility Verifier
    检查输入输出契约、版本、配置、能力和配对关系

Data Governance Service
    管理采集计划、数据血缘、权限、质量和用途

Deterministic Execution Gate
    执行权限、状态、阈值和放行检查

Runtime Monitor
    采集模型、链路、系统和资源运行状态

Fallback Controller
    在 Agent 不可用或模型失效时独立回退
```

### 5.2 两种控制环

#### 快速控制环

快速控制环不应依赖 LLM 或远程 API，负责：

- HARQ；
- 快速链路自适应；
- 即时功控；
- 基础模型推理；
- 本地异常检测；
- 紧急回退。

#### 慢速生命周期环

慢速生命周期环可以使用 LLM，负责：

- 模型评估；
- 数据收集计划；
- 模型切换；
- 在线或特定场景微调规划；
- 跨小区迁移；
- 模型发布和验收；
- 复杂故障诊断。

```text
快速环：信号/状态 → 确定性控制器 → 即时动作

慢速环：日志/指标/报告 → Agent 规划 → 验证器 → 生命周期动作
```

## 6. BS/gNB 侧 Agent 设计

### 6.1 主要职责

BS 侧 Agent 负责全局管理，但不应绕过 UE 本地约束。其职责包括：

- 维护候选模型集合；
- 根据小区和 UE 状态筛选候选模型；
- 生成评估和补测计划；
- 读取跨 UE 的聚合性能；
- 管理跨小区和跨厂商模型版本；
- 判断是继续运行、微调、切换还是回退；
- 创建双侧模型切换事务；
- 协调 UE 侧准备和确认；
- 生成共同生效计划；
- 记录发布、监测和回退证据。

### 6.2 BS Agent 的内部模块

```text
BS Agent
├── 任务理解器
├── 证据检索器
├── KPI 与评估规划器
├── 模型选择器
├── LCM 编排器
├── 跨 UE/跨小区协调器
├── 成本收益估计器
├── 计划生成器
├── 报告与审计生成器
└── 工具调用策略层
```

LLM 适合处理：

- 异构模型说明；
- 非结构化测试报告；
- 不同厂商的适用条件；
- 复杂的部署约束；
- 证据缺口解释；
- 下一项补测选择；
- 多种生命周期路径的比较。

确定性程序负责：

- 数值 KPI 计算；
- 模型契约验证；
- 版本匹配；
- 设备能力判断；
- 权限和预算检查；
- 阈值判定；
- 事务状态推进。

### 6.3 BS Agent 不应拥有的权限

- 修改独立验证器逻辑；
- 关闭 UE 本地隐私策略；
- 强制激活 UE 明确拒绝的模型；
- 越过模型签名和版本检查；
- 直接修改快速无线控制器；
- 将自然语言报告当作兼容性证明；
- 在没有回退目标时强制发布新模型。

### 6.4 LCM 管理模式

BS Agent 可以同时支持两种候选管理方式：

#### A. Model ID-based LCM

模型以明确的模型 ID、版本、输入输出契约和适用条件注册。适合：

- CSI encoder/decoder 配对；
- 需要明确版本控制的双侧模型；
- 跨厂商兼容矩阵；
- 模型下载、撤销和回退。

#### B. Functionality-based LCM

Agent 不直接要求某个固定模型 ID，而是声明需要某种功能，例如：

- 低开销 CSI 反馈；
- CSI 预测；
- 波束预测；
- AI 辅助信道估计。

然后由 BS Agent 根据当前 UE 能力、场景和资源约束选择满足功能契约的模型或模型组合。

两种模式不应互斥：功能模式适合跨厂商和模型替换，模型 ID 模式适合精确复现、配对和审计。本文的模型注册表同时保存功能标签和具体模型 ID。

### 6.5 BS 侧 LCM 子模块

BS 侧 LCM 子模块可进一步划分为：

```text
BS LCM Agent
├── Model Selector       模型选择器
├── Performance Monitor  性能监测器
├── Fallback Planner     回退规划器
├── Update Scheduler     更新调度器
├── Evidence Planner     证据与补测规划器
└── Transaction Manager  双侧事务管理器
```

其中：

- `Model Selector` 负责在满足契约的候选中选择模型；
- `Performance Monitor` 区分短时波动和真实性能退化；
- `Fallback Planner` 选择鲁棒模型、降级功能或传统方案；
- `Update Scheduler` 结合维护窗口、数据充分性和切换成本安排更新；
- `Evidence Planner` 判断是否需要额外测试，不允许只凭 LLM 判断发布；
- `Transaction Manager` 管理 UE 与 BS 的准备、提交、确认和回退。

## 7. UE 侧 Agent Runtime 设计

### 7.1 主要职责

UE 侧组件不承担全局规划，而承担本地事实确认：

- 上报 UE 能力；
- 上报当前模型、版本和运行状态；
- 检查候选模型能否在本地运行；
- 检查输入输出格式和反馈契约；
- 检查内存、算力、推理时延和功耗预算；
- 管理本地数据采集权限；
- 生成本地性能摘要；
- 执行本地预验证；
- 在本地发现异常时拒绝激活；
- 支持旧模型或传统方案快速回退。

### 7.2 UE 侧不一定需要完整 LLM

UE 侧可以采用三种实现等级：

| 等级 | 实现 | 适用场景 |
|---|---|---|
| L0 | 确定性状态机 | 最小实现和资源极受限设备 |
| L1 | 轻量策略模型 + 状态机 | 需要本地异常分类和简单策略选择 |
| L2 | 小型本地 LLM/蒸馏模型 + 验证器 | 需要解释复杂本地日志和数据策略 |

第一版建议使用 L0 或 L1。只要本地状态、能力和资源检查能够完成，就不需要为了“Agent 对称性”在 UE 上部署完整 LLM。

### 7.3 UE Agent 的本地安全门

UE 侧所有模型激活请求都应经过本地安全门：

```text
收到 BS 请求
    ↓
签名和版本检查
    ↓
输入输出契约检查
    ↓
设备能力检查
    ↓
本地资源预算检查
    ↓
本地隐私和数据策略检查
    ↓
候选模型本地验证
    ↓
READY 或 REJECT
```

本地安全门必须可以在 BS Agent 或远程 LLM 不可用时独立运行。

## 8. 两侧职责与权限矩阵

| 功能 | BS Agent | UE Agent | 确定性验证器 | 实时控制器 |
|---|---:|---:|---:|---:|
| 读取全局性能 | 是 | 否 | 否 | 否 |
| 读取本地资源状态 | 请求 | 是 | 是 | 否 |
| 生成评估计划 | 是 | 可提供本地约束 | 否 | 否 |
| 计算 KPI | 调用工具 | 提供本地数据 | 是 | 否 |
| 模型输入输出检查 | 请求 | 执行本地检查 | 是 | 否 |
| 模型配对检查 | 提交候选 | 确认本地端 | 是 | 否 |
| 模型切换建议 | 是 | 可拒绝 | 是 | 否 |
| 模型最终本地激活 | 否 | 请求验证后执行 | 是 | 否 |
| 紧急回退 | 可发起 | 必须可执行 | 放行 | 独立执行 |
| 修改安全策略 | 否 | 否 | 否 | 否 |
| 修改实时调度 | 否 | 否 | 否 | 是 |

核心原则是：

> BS Agent 决定“值得不值得做”，UE Agent 决定“本地能不能做”，验证器决定“是否允许做”，执行器决定“如何安全地做”。

## 9. 结构化协同协议

### 9.1 设计原则

两侧 Agent 不应通过自然语言直接协商。协议应具备：

- 明确的消息类型；
- 明确的版本字段；
- 明确的事务 ID；
- 可验证的模型摘要；
- 可追踪的证据引用；
- 可重复的状态转移；
- 过期和撤销机制；
- 失败和回退分支。

### 9.2 主要消息类型

```text
CAPABILITY_REPORT
MODEL_OFFER
MODEL_QUERY
EVALUATION_REQUEST
EVALUATION_RESULT
PREPARE_REQUEST
PREPARE_RESULT
READY
REJECT
COMMIT_REQUEST
COMMIT_ACK
MONITOR_REPORT
DEGRADE_ALERT
ROLLBACK_REQUEST
ROLLBACK_ACK
```

### 9.3 模型切换事务

推荐的切换流程为：

```text
DISCOVER
    ↓
PROPOSE
    ↓
PREPARE
    ↓
LOCAL_VALIDATE
    ↓
READY / REJECT
    ↓
COMMIT
    ↓
ACTIVATE
    ↓
MONITOR
    ↓
ACCEPT / ROLLBACK
```

### 9.4 状态语义

| 状态 | 含义 |
|---|---|
| `REGISTERED` | 模型已登记，但未证明适用于目标设备和场景 |
| `PROFILED` | 模型输入输出、资源和适用条件已描述 |
| `EVALUATING` | 正在执行模型、链路或系统评估 |
| `PREPARED` | 模型已下载/加载，但未激活 |
| `LOCAL_VALIDATED` | 本地契约和资源检查通过 |
| `READY` | 两端均满足共同生效条件 |
| `ACTIVATED` | 模型已经开始服务 |
| `MONITORING` | 正在收集部署后性能和资源指标 |
| `ACCEPTED` | 部署后验收通过 |
| `DEGRADED` | 性能退化，但尚未触发回退 |
| `ROLLED_BACK` | 已回退到旧模型或传统方案 |
| `REJECTED` | 因证据、兼容性、权限或资源不足而拒绝 |

“下载完成”不能直接等价于“可以运行”，更不能等价于“已经共同生效”。

## 10. 模型卡与证据对象

### 10.1 模型卡

每个候选模型至少需要保存：

```json
{
  "model_id": "csi-compressor-v3",
  "version": "3.1.0",
  "model_location": "two-sided",
  "vendor_scope": "vendor-a",
  "input_contract": {
    "signal_type": "CSI-RS",
    "antenna_ports": 32,
    "band": "3.5GHz",
    "feedback_format": "type-II",
    "quantization": "int8"
  },
  "output_contract": {
    "output_type": "reconstructed-csi",
    "shape": "32xN"
  },
  "supported_scenarios": ["UMi", "indoor-office"],
  "resource_requirements": {
    "ue_memory_mb": 64,
    "ue_inference_latency_ms": 2.0,
    "max_power_mw": 500
  },
  "paired_models": ["decoder-v3.1.0"],
  "fallback_model": "legacy-csi-codebook",
  "evidence_refs": ["eval-2026-0012", "compat-2026-0021"]
}
```

### 10.2 证据对象

证据不能只保存自然语言结论，而应保存：

- 证据 ID；
- 来源工具；
- 生成时间；
- 模型版本；
- 设备和配置；
- 场景；
- 指标和单位；
- 随机种子或测试批次；
- 有效期；
- 允许的用途；
- 是否为仿真、实测或人工说明；
- 是否经过独立验证。

```json
{
  "evidence_id": "eval-2026-0012",
  "evidence_type": "system_evaluation",
  "source": "evaluation_engine",
  "created_at": "2026-10-19T10:00:00+08:00",
  "model_version": "3.1.0",
  "scenario": "UMi",
  "device_profile": "ue-class-b",
  "metrics": {
    "throughput_mbps": 812.4,
    "feedback_overhead_ratio": 0.18,
    "inference_latency_ms": 1.7
  },
  "valid_until": "2026-10-26T10:00:00+08:00",
  "verified": true,
  "allowed_use": ["release_decision", "regression_check"]
}
```

### 10.3 功能级模型注册

为了同时支持“需要什么能力”和“具体使用哪个实现”，模型注册表还需要维护功能级索引：

```json
{
  "functionality": "low-overhead-csi-feedback",
  "required_contract": {
    "max_feedback_overhead_ratio": 0.2,
    "max_inference_latency_ms": 2.0,
    "required_output": "reconstructed-csi"
  },
  "candidate_models": [
    "candidate-model-a",
    "candidate-model-b"
  ],
  "selection_policy": "evidence-and-cost-aware",
  "fallback": "legacy-csi-codebook"
}
```

功能级索引解决的是“需要什么能力”，模型 ID 解决的是“具体使用哪个实现”。Agent 必须保留二者之间的映射证据，不能因为功能名称相同就认为模型天然兼容。

## 11. 数据收集与隐私设计

### 11.1 数据收集职责

| 数据任务 | BS Agent | UE Agent |
|---|---|---|
| 定义全局数据需求 | 负责 | 提供本地约束 |
| 定义本地采样字段 | 请求 | 执行和裁剪 |
| 判断是否允许上传 | 不可绕过 | 本地决定 |
| 上传聚合统计 | 负责协调 | 可上传授权结果 |
| 保存原始本地样本 | 不应默认要求 | 按本地策略保存 |
| 生成跨 UE 数据集 | 负责聚合 | 提供脱敏摘要或样本 |
| 训练/验证/测试划分 | 负责全局计划 | 提供本地分布约束 |
| 数据质量检查 | 全局统计 | 本地格式和完整性 |

### 11.2 数据血缘

每个样本或聚合统计至少要绑定：

```text
样本/统计值
→ 采集实体
→ UE/小区标识范围
→ 时间戳
→ 场景和配置
→ 模型版本
→ 数据用途
→ 标签来源
→ 是否脱敏
→ 是否允许上传
→ 质量检查结果
```

### 11.3 隐私边界

UE Agent 必须能够拒绝以下操作：

- 上传未经授权的原始信号；
- 上传可识别设备或用户的数据；
- 上传超过用途范围的数据；
- 继续执行已经撤销的数据采集任务；
- 使用本地数据训练未授权模型。

BS Agent 应优先使用：

- 聚合统计；
- 脱敏特征；
- 经授权的统计量或特征摘要；
- 受控的样本子集；
- 由 UE 明确授权的目标数据。

### 11.4 联邦学习与隐私预算：暂不纳入第一版

联邦学习、差分隐私、隐私预算和参与者选择属于数据治理方向的后续扩展，不是当前双 Agent 生命周期闭环的必要条件。

第一版只保留与标准直接相关的约束：数据请求要说明用途、范围、来源、质量和成本；UE 能够拒绝未授权或超出本地策略的数据任务；LLM 不得绕过确定性权限门。后续若单独研究 FL/DP，应另立实验边界，并由确定性隐私会计器承担预算检查，不能把隐私决策交给 LLM。

### 11.5 数据最小化决策

对于 CSI 压缩、波束预测等任务，Agent 应优先生成“最小必要数据计划”，而不是默认请求所有 UE 数据。例如：

| 任务 | 首选数据 | 默认不请求的数据 |
|---|---|---|
| CSI 压缩 | CSI-RS、参考信号观测、必要配置 | 精确位置、应用内容 |
| 波束预测 | 波束测量、历史波束选择、移动性摘要 | 原始用户业务内容 |
| 场景泛化评估 | 场景类别、设备能力、匿名化性能统计 | 可识别用户轨迹 |

Agent 可以提出最小化建议，但数据字段是否允许采集必须由 UE 本地策略和确定性权限门决定。

## 12. 典型运行流程：以 CSI 为例的模型退化与切换

### 12.1 触发

UE 和 BS 侧监测到：

- CSI 重构误差持续升高；
- CSI 反馈开销没有下降到预期水平；
- 推理时延超过预算；
- 吞吐量低于传统基线；
- 新小区或新频段上的性能明显退化。

### 12.2 BS Agent 处理

BS Agent 读取：

- 当前模型和版本；
- UE 能力和本地资源状态；
- 目标小区和邻近小区统计；
- 候选模型注册信息；
- 已有评估证据；
- 当前维护窗口和切换预算。

然后判断问题更接近：

- 场景漂移；
- 训练数据分布变化；
- 模型版本失配；
- UE 配置变化；
- 输入格式变化；
- 资源不足；
- 监测数据异常。

### 12.3 候选动作

```text
A. 继续观察
B. 增加数据采集
C. 仅做 BS/网络侧兼容适配
D. BS 侧微调
E. UE 侧微调
F. UE 与 BS 双侧更新
G. 切换到场景模型
H. 回退传统 CSI 方案
```

### 12.4 UE Agent 本地检查

对每一个候选模型，UE Agent 检查：

- 输入字段是否齐全；
- 天线端口和频段是否匹配；
- 反馈格式是否匹配；
- 模型量化格式是否支持；
- 内存是否足够；
- 推理时延是否满足要求；
- 功耗是否在预算内；
- 本地数据策略是否允许采集或微调；
- 本地回退模型是否存在。

### 12.5 发布判定

只有在以下条件同时满足时才允许共同激活：

```text
输入输出契约兼容
AND
两侧模型配对正确
AND
UE 本地资源满足
AND
目标场景评估通过
AND
旧场景回归没有超过损失阈值
AND
切换成本在预算内
AND
回退路径已准备
AND
两侧都返回 READY
```

### 12.6 CSI 评估链路：研究实现，不是标准工具链

在 CSI 用例中，模型评价应放回完整的通信流程，而不是只比较 NMSE。实现时可以将工具按以下职责组织，但不预设具体 API 名称，也不把它们写成标准要求：

```text
候选模型/模型卡
    ↓
输入输出与两侧配对检查
    ↓
信道估计 → CSI 压缩/预测 → 量化与反馈
    ↓
gNB 重建 → 预编码/调度
    ↓
链路 KPI、系统 KPI、推理/反馈/切换成本
    ↓
带证据引用的评估与发布报告
```

其中，兼容性检查、性能仿真、结果查询和报告生成应当是可审计的确定性工具；BS Agent 负责决定下一项检查或补测，UE Runtime 负责提供本地能力、资源和可采数据边界。标准检索可以作为离线知识库能力，但不是运行时 CSI 工具链的必要节点。

CSI 工作流至少应显式表示：

```text
信道估计 → CSI 压缩 → 量化 → PUCCH/PUSCH 反馈
→ gNB 重建 → 预编码/调度 → 链路与系统 KPI
```

这样可以把“模型精度很好”转换为可检查的端到端问题：压缩收益是否抵消了反馈、推理、重建和部署开销。

## 13. 生命周期状态机设计

### 13.1 全局状态机

```text
REGISTERED
    ↓
PROFILED
    ↓
EVALUATING
    ├── 证据不足 → NEED_MORE_EVIDENCE
    ├── 不兼容 → REJECTED
    └── 评估通过 → PREPARING
                         ↓
                 UE_LOCAL_VALIDATION
                         ├── 失败 → REJECTED
                         └── 通过 → READY_WAIT
                                         ↓
                                  JOINT_COMMIT
                                         ├── 一端失败 → ABORTED
                                         └── 成功 → ACTIVATED
                                                      ↓
                                                  MONITORING
                                                      ├── 正常 → ACCEPTED
                                                      ├── 可适配 → ADAPTING
                                                      ├── 可切换 → SWITCHING
                                                      └── 严重退化 → ROLLING_BACK
```

### 13.2 状态转移必须带条件

每次状态转移需要记录：

- 当前状态；
- 目标状态；
- 触发原因；
- 触发者；
- 证据引用；
- 必需验证；
- 当前模型版本；
- 目标模型版本；
- 事务超时；
- 失败后的回退状态。

## 14. 失败场景与处理策略

### 14.1 BS 认为可用，但 UE 本地拒绝

原因可能是：

- UE 内存不足；
- 输入配置不匹配；
- 模型签名无效；
- 本地功耗预算不足；
- 本地隐私策略不允许采集数据。

处理方式：

```text
UE 返回 REJECT
→ BS 记录具体原因
→ Agent 重新选择候选动作
→ 不得把拒绝改写成 READY
```

### 14.2 UE 已准备，但 BS 状态发生变化

例如：

- 维护窗口结束；
- 目标模型被撤销；
- 小区负载突然变化；
- 另一项发布事务先完成。

处理方式：

- 检查事务版本和过期时间；
- 重新读取 BS 当前状态；
- 旧计划自动失效；
- 不允许使用过期计划直接提交。

### 14.3 一侧激活成功，另一侧失败

这是双侧模型的关键风险。处理方式：

- 采用准备阶段而不是直接激活；
- 共同提交必须有事务 ID；
- 设定最大等待时间；
- 一侧提交失败时执行中止或回退；
- 记录半完成事务；
- 不将半完成状态报告为成功发布。

### 14.4 模型运行性能下降

分级处理：

```text
轻微退化 → 增加监测
持续退化 → 采集补充数据
可解释漂移 → 特定场景微调
明显失配 → 切换候选模型
安全或业务风险 → 立即回退
```

### 14.5 Agent 或 API 不可用

Agent 不可用时：

- 当前已激活模型继续运行；
- 快速控制器继续工作；
- UE 本地回退控制器保持可用；
- 不执行新的高风险模型切换；
- 恢复后重新检查证据和版本状态。

## 15. 评估方法

### 15.1 系统对照

至少比较以下方案：

1. 静态固定模型；
2. 只按照离线精度选择模型；
3. 只由 BS Agent 决策；
4. BS Agent + UE 确定性 Runtime；
5. BS Agent + UE 轻量 Agent；
6. 规则系统 + 固定测试流水线；
7. BS/UE 双 Agent + 独立验证器。

### 15.2 主要研究假设

#### H1：双侧本地验证能够减少错误发布

在 BS 获得的信息不完整或过期时，UE 侧本地验证应减少：

- 不兼容模型激活；
- UE 资源超预算；
- 半完成双侧切换；
- 本地隐私策略被绕过。

#### H2：证据驱动的双 Agent 能减少不必要补测

在相同测试预算下，Agent 应通过识别最有价值的缺口，达到更高的有效发布率；或者在相同有效发布率下减少测试次数和测试成本。

#### H3：净收益决策优于精度贪心决策

当模型精度、反馈开销、推理成本、切换中断和回退风险同时存在时，净收益策略应比“选择精度最高模型”减少无效切换。

#### H4：分层 Agent 优于对称双 LLM

完整 BS Agent + 轻量 UE Runtime 应在资源、时延、可解释性和错误隔离方面优于 BS/UE 两侧各部署完整 LLM。

### 15.3 指标

#### 决策正确性

- 有效发布率；
- 错误发布率；
- 错误模型配对率；
- 本地拒绝正确率；
- 过期证据使用率；
- 不必要拒绝率。

#### 生命周期性能

- 模型切换成功率；
- 半完成事务数量；
- 切换中断时长；
- 回退次数；
- 模型退化持续时间；
- 部署后验收通过率；
- 跨小区模型连续性。

#### 系统开销

- 测试次数；
- 补测成本；
- Agent 调用次数；
- Agent 端到端时延；
- 模型传输开销；
- 数据收集开销；
- UE 计算、存储和功耗开销。

#### 无线业务效果

- 吞吐量；
- BLER；
- CSI 反馈开销；
- 推理时延；
- 用户业务中断；
- 旧场景性能损失；
- 跨场景泛化性能。

## 16. 实验场景设计

### 16.1 基础场景

固定：

- 选定用例的 2-4 个候选模型；
- 该用例的传统或非 AI 基线；
- 2 类 UE 能力；
- 2-3 个信道场景；
- 固定模型版本和测试工具；
- 固定模型配对关系；
- 固定发布窗口和测试预算。

### 16.2 必须覆盖的异常

- 目标模型证据缺失；
- UE 内存不足；
- 输入输出格式不匹配；
- BS 与 UE 模型版本不一致；
- 一端准备成功、另一端失败；
- 证据在测试期间过期；
- 小区切换导致场景漂移；
- 在线微调数据不足；
- Agent API 失败；
- 模型性能超过退化阈值；
- 回退模型不可用；
- 竞争发布事务同时发生。

### 16.3 动态状态变化

在 Agent 规划和工具调用期间改变：

- UE 能力；
- 当前模型版本；
- 目标小区；
- 数据权限；
- 维护窗口；
- 模型撤销状态；
- 网络负载；
- 可用回退版本。

验证 Agent 是否能够在共同激活前重新检查状态，而不是沿用旧计划。

## 17. 实现路线

### Phase 0：单机离线原型

目标：验证 Agent 能否读懂模型说明并生成可检查发布计划。

组件：

- 固定模型卡；
- 固定测试报告；
- 单个 BS 侧 Agent；
- 兼容性检查器；
- 证据对象存储。

输出：

- 证据缺口清单；
- 补测计划；
- 模型发布申请；
- 拒绝和回退理由。

### Phase 1：BS Agent + UE Runtime

目标：引入 UE 本地能力、资源和隐私检查。

新增：

- UE 能力报告；
- UE 模型卡；
- 本地验证器；
- `READY/REJECT` 消息；
- 本地回退控制器。

### Phase 2：双侧模型事务

目标：实现准备、共同提交、确认和回退。

新增：

- 事务 ID；
- 版本和过期时间；
- 两端准备状态；
- 共同提交；
- 半完成事务处理；
- 部署后验收。

### Phase 3：动态场景和证据驱动补测

目标：让 Agent 根据场景漂移和证据缺口主动安排补测。

新增：

- 场景变化检测；
- 数据收集任务；
- 泛化测试；
- 在线/特定场景微调计划；
- 补测预算和停止条件。

### Phase 4：多 UE、跨小区和跨厂商扩展

目标：验证 BS Agent 的全局协调能力。

新增：

- 多 UE 模型分组；
- 跨小区模型迁移；
- 跨厂商模型配对；
- 局部模型与通用模型共存；
- 全局收益与个体收益权衡。

## 18. 主要研究风险

### 18.1 双 Agent 只是系统拆分，没有新的研究机制

如果 BS Agent 只是调用工具，UE Agent 只是返回能力字段，那么工作可能只是工程架构。

必须突出可验证机制，例如：

- 信息不对称下的协同决策；
- 证据缺口驱动的主动补测；
- 净收益驱动的生命周期路径选择；
- 双侧共同生效和半完成事务恢复；
- 本地约束与全局目标的冲突解决。

### 18.2 LLM 贡献不明显

如果所有模型卡和测试报告已经高度结构化，固定规则系统可能足够。此时应比较：

- 纯规则系统；
- 结构化流水线；
- 单 LLM Agent；
- 双 Agent；
- 双 Agent + 独立验证器。

如果 LLM 只提高报告可读性，却不改善补测选择、发布正确率或生命周期成本，就不应把 LLM 作为主要创新点。

### 18.3 真实无线数据和模型不足

第一版可以使用：

- 固定候选模型；
- 固定信道数据；
- 合成模型卡；
- 可复现的仿真工具；
- 明确标注为管理逻辑仿真的测试数据。

但不能将管理仿真结果表述为真实无线网络收益。后续需要逐步补充真实设备或可信无线仿真证据。

### 18.4 Agent 进入实时路径

必须明确：

- LLM 不参与时隙级控制；
- 远程 API 不属于动作必经路径；
- Agent 超时不应导致业务停止；
- 当前模型和传统回退机制独立运行；
- 新模型必须准备并验证后才允许激活。

## 19. 建议的最终问题定义

推荐使用以下问题定义作为该扩展方向的主问题：

> 在 UE 与 BS 掌握局部且不完全一致的信息、模型评估证据有限、设备能力异构以及模型切换具有成本的条件下，BS 主 Agent 与 UE 轻量 Agent 能否通过证据驱动的协同协议，选择低成本且可验收的模型生命周期动作，同时避免不兼容激活、半完成切换和无线业务退化？

可进一步拆分为：

### Q1：局部信息不完整时如何形成一致的模型状态

BS 看到全局统计，UE 看到本地资源和数据。如何避免两侧对模型版本、适用条件和运行状态产生不一致理解？

### Q2：何时需要双侧更新

当网络侧兼容适配已经足够时，不应强制 UE 更新；当输入输出契约变化时，又必须处理两端配对和共同生效。如何根据契约变化和收益成本决定更新范围？

### Q3：如何用最少补测支撑共同激活

在测试预算有限时，Agent 该优先检查兼容性、目标场景性能、旧场景回归、设备资源还是部署后验收？什么时候可以停止补测？

### Q4：如何保证双侧切换可回退

当 UE 已准备而 BS 未准备，或一侧已经激活而另一侧失败时，如何让事务回到可控状态，并准确记录半完成事务？

### Q5：双 Agent 是否比单 Agent 更有价值

在相同模型、工具、候选集、权限和测试预算下，比较单 BS Agent 与 BS/UE 双 Agent 是否能够降低错误发布、切换失败和本地资源超预算。

## 20. 推荐的第一版系统边界

第一版应保持以下边界：

```text
一个边界清晰的无线 AI/ML 用例
两个或三个固定候选模型
一个 BS 主 Agent
一个 UE 轻量 Runtime
一个模型注册表
一个兼容性验证器
一个评估引擎
一个生命周期状态机
一个独立回退控制器
```

第一版支持的动作：

- 继续运行；
- 补测；
- BS 侧适配；
- 按模型位置执行网络侧、UE 侧或双侧模型切换；
- 传统方案回退。

第一版暂不支持：

- 自动生成模型权重；
- 多用例统一优化；
- UE 部署完整 LLM；
- Agent 自主修改协议；
- LLM 直接控制快速无线环；
- 未经验证的自动发布。

## 21. 总结

BS/UE 双 Agent 的合理设计不是在两侧复制两个相同的聊天模型，而是建立一个分层、非对称、可验证的协同系统：

```text
BS Agent：全局目标、评估规划、模型选择、生命周期编排

UE Agent：本地能力、数据隐私、资源约束、本地验证和回退

验证器：兼容、版本、权限、阈值和状态一致性检查

执行器：准备、共同激活、监测和回退

实时控制器：独立完成时隙级无线控制
```

该设计能够同时覆盖 R1-2508811 第三章的：

- 评估与 KPI；
- 模型生命周期管理；
- 数据收集与数据治理。

但研究贡献应集中在“证据驱动的端网生命周期协同”上，而不是泛化为一个可以处理所有无线问题的多 Agent 平台。最稳妥的路线是先选择一个边界清晰、数据和 KPI 可获得的用例，以该用例的单侧模型作为强基线、双侧模型作为受控扩展；CSI 压缩、CSI 预测、低开销 DMRS、波束管理和定位增强都可以成为候选，但不应在架构层预先指定其中任何一个。
