## 10. 基准、评测协议与证据校准

<a id="s10-1"></a>

### 10.1 评测必须回答的四个不同问题

1. **最终预测质量**：AUC / AUCPR / RMSE / logloss 等是否提升？
2. **自动化水平**：是否无需人工编写中间步骤？失败时能否自我恢复？
3. **工作效率**：完成任务需要多少 wall-clock 时间、GPU 小时、人工时间和 token？
4. **交付可靠性**：能否复跑、是否产生泄漏、是否生成可部署模型、是否满足约束？

**单个 leaderboard 排名只回答其中一部分**。LLM agent 可能因为不停训练而提升预测分数，却在成本和资源效率上劣于简单 AutoML；另一个 agent 可能更会执行任务，但生成的模型并不优于固定 pipeline。

<a id="s10-2"></a>

### 10.2 AMLB：经典 AutoML 的公平评测范式

**文献**：Gijsbers et al., *AMLB: an AutoML Benchmark*，JMLR 2024。[R13]

论文介绍可扩展的 AutoML 评测框架，对 **9 个知名 AutoML 系统**进行比较，覆盖 **71 个分类与 33 个回归任务**，分析预测性能、推理时间、系统失败以及不同数据任务下排序变化。

**方法论启示**：

- 统一硬件、时间预算、数据划分、处理流程；
- 报告失败率而不是只挑成功任务；
- 模型训练性能之外还须报告推理性能；
- 不同算法在不同任务子集上排名可能变化；
- 多任务平均得分需要透明归一化，避免某个量纲占据主导。

**推荐使用**：传统 AutoML baseline 的综合测试套件，也可作为 Agentic AutoML 的固定建模核心对照集。

<a id="s10-3"></a>

### 10.3 MLE-bench：机器学习工程 Agent 的关键基准

**文献**：Chan et al., *MLE-bench: Evaluating Machine Learning Agents on Machine Learning Engineering*，arXiv 2024，ICLR 2025。[R30]

**任务内容**：整理 **75 项 Kaggle 机器学习竞赛相关任务**，覆盖训练模型、处理数据、运行实验、生成提交文件，利用公开 Kaggle 排名建立人类参照。

**2024 原论文结果**：当时最好的已评估配置（**AIDE scaffold + o1-preview**）在 **16.9%** 的比赛上达到了至少铜牌等级。这只是作者在其原始实验设置下的结果，不代表 2026 年最好的可用模型能力。[R30], [R45]

<a id="s2026"></a>

## 2026 年官方仓库榜单的注意事项

在查阅时，OpenAI 官方 `openai/mle-bench` 仓库有一个标注 **2026-04-24** 的更新：项目因需要改进公平可比的提交流程而**暂不接受新 leaderboard 提交**。仓库榜单中的若干历史提交包括：[R31]

| 榜单显示项目 | 模型/主体（官方表述） | `All (%)` | 运行预算 | 提交时间 | 应如何解读 |
|---|---|---:|---:|---|---|
| Famou-Agent 2.0 | Gemini-3-Pro-Preview | **64.44 ± 1.18** | 24 h | 2026-02-23 | 仓库所列提交分数，不是本文复现 |
| AIBuildAI | Claude-Opus-4.6 | **63.11 ± 0.44** | 24 h | 2026-03-06 | 提交条件及源码开放程度需核对 |
| CAIR MARS+ | Gemini-3-Pro-Preview | **62.67 ± 0.77** | 24 h | 2026-02-17 | 不同结构/工具栈，不是单模型对照 |
| MLEvolve | Gemini-3-Pro-Preview | **61.33 ± 1.33** | 12 h | 2026-02-14 | 预算不同，不能直接排序为效率最优 |

**极重要的限制**：表格是官方 README **在本次查阅时**展示的提交快照，不保证覆盖所有未提交研究，也不代表已独立完成全量审计。仓库自己提示需要改进公平性；不同主体的 GPU 环境、工具栈、交互次数、并发和开源程度可能不同。因此不能将 2024 年 16.9% 与 2026 年 64.44% 当成**其他变量严格不变**的模型性能进步曲线。

#### 官方推荐协议（据仓库文档）

- 重复至少 **3 个随机种子**，以 `Any Medal (%)` 的平均值和标准误形式报告；
- 参考资源设置是 **24 小时、36 vCPU、440 GB RAM、1 张 24 GB A10 GPU**；
- 报告 Low、Medium、High、All 的分组成绩；
- Lite 子集为 **22 个低复杂度竞赛**；
- 必须报告使用的 scaffold、模型版本、资源预算和任务快照。[R31]

企业自研 Agent 可以先从 Lite 开始，确保评测无环境/凭据/数据准备错误，再扩大到全量；不要在每轮代码改动后重跑全部 75 项任务。

<a id="s10-4"></a>

### 10.4 DSBench：侧重真实数据分析与建模任务

**文献**：Jing et al., *DSBench: How Far Are Data Science Agents from Becoming Data Science Experts?*，ICLR 2025。[R32]

包含 **466 个数据分析任务**与 **74 个建模任务**，更重视长上下文、多表、多模态信息与端到端分析。论文报告其测试系统里，表现最佳的 agent 完成约 **34.12% 的数据分析任务**；建模任务的指标体系不同，因此不能将这个数和 MLE-bench 奖牌率直接比较。

**适用**：评估 Agent 是否能理解数据、综合分析、输出结果。若目标是开发“一句话完成数据清洗+EDA+模型+报告”的系统，比只评估 HPO 更贴近产品。

<a id="s10-5"></a>

### 10.5 MLGym / MLRC-Bench：让 Agent 的研究能力可被检验

**MLGym**，Nathani et al.，2025 年 arXiv，提供 **13 个跨 CV/NLP/RL/博弈等领域的开放 ML 研究任务**，强调真实训练、假设与反复试验。作者报告当时的模型多数改进来自参数优化等熟悉手段，尚难稳定提出突破性的新算法/架构。[R37]

**MLRC-Bench**，Zhang et al.，2025 年 arXiv，面向研究型 ML 竞赛，首批 **7 个任务**；论文摘要指出被评估的最佳 agent 只填补从 baseline 到最佳人类成绩差距的 **9.3%**，并强调 LLM 给出的“创新性”评价可能与客观竞赛收益不一致。[R43]

**启示**：当目标升级为自动研究（AI for AI），不要仅用“生成了一个新算法名称”证明创新，应当使用**可复现的数值增益、严格对照、代码正确性和研究问题的新颖性**联合评价。

<a id="s10-6"></a>

### 10.6 AutoML Agent 评估指标总表

| 指标层 | 推荐指标 | 定义/方向 | 解释 |
|---|---|---|---|
| 预测质量 | normalized regret | `(score_oracle-score_agent)/(score_oracle-score_baseline)`（分母须为正） | 不同任务汇总时参考，以正确方向做归一化 |
| 预测质量 | win/tie/loss vs baseline | 同预算下多 seed 统计 | 不依赖跨任务绝对量纲 |
| 交付质量 | valid submission rate | 正确提交或产物比例 ↑ | 避免失败任务从平均分中消失 |
| 交付质量 | deployable artifact rate | 通过离线验收的模型比例 ↑ | 代码能跑不等于可上线 |
| 成本 | GPU-hours / CPU-hours | 资源消耗 ↓ | 对硬件异构进行标注 |
| 成本 | LLM tokens / API cost | 推理调用成本 ↓ | 不是训练算力替代量 |
| 时效 | time to first valid model | 首个合格模型耗时 ↓ | 工业场景非常关键 |
| 时效 | best-so-far performance curve | 随预算变化的最优指标 ↑ | 横向比较最稳健的视图之一 |
| 可靠性 | runtime failure rate | 试验运行失败数/总试验数 ↓ | 分类语法/OOM/依赖/环境 |
| 可靠性 | leakage incident rate | 被审计发现泄漏次数 ↓ | 严重性最高的错误类别之一 |
| 可复现 | seed variance / rerun success | 3–5 seed 方差及回放成功率 | 避免幸运运行 |
| 治理 | policy violation rate | 权限、网络、数据、资源违规 ↓ | 强制不容越线 |
| 研究能力 | gap-to-best-human closed | 与人类竞赛上限差距缩短 ↑ | 上限可能受榜单污染影响 |
| 搜索效能 | improvement per trial / dollar | 单位成本最佳表现改善 ↑ | 为 Agent 与优化器协同定量 |

**示例定义建议**：对每个任务绘制横轴为累计总成本（例如美元或统一 GPU 小时）、纵轴为严格同一验证方式下的 best-so-far 指标。只在预算、任务划分、资源可比时进行 AUC 曲线比较。多个任务汇总时使用成对置信区间和非参数检验，而不仅看平均值。

<a id="s10-7"></a>

### 10.7 必须警惕的六类基准失真

1. **数据污染（contamination）**：agent 或底座模型可能在预训练中看过公开竞赛答案或高分脚本。
2. **验证集反复自适应使用**：尝试越多，越容易偶然找到在验证集上表现好的错误模型。
3. **不同预算**：12h 与 24h、CPU 与 GPU、闭源 API 与本地 7B 必须分开报告。
4. **任务筛选**：失败或无结果任务被排除，造成 survivor bias。
5. **奖励替代**：agent 输出“解决了问题”不能当作实际通过数据校验；代码执行通过也不等于真实预测质量。
6. **版本漂移**：Kaggle 数据/依赖、AutoML 框架、LLM 版本与 official leaderboard 持续变化；没有环境 digest 很难复跑。

## 5. Benchmark 景观与它们测不到的东西

| Benchmark | 规模 | 强项 | 测不到 |
|---|---|---|---|
| MLE-bench（`2410.07095`） | 75 Kaggle 竞赛 + 人类奖牌对照 | 真实工程链路；含污染分析与资源放缩 | 方法学正确性；决策质量；预算执行 |
| MLAgentBench（`2310.03302`） | 13 个实验任务 | 面向"做实验"本身 | 规模与统计功效 |
| RE-Bench（`2411.15114`） | 7 环境 + 61 位专家 71 次 8h | 少见的人类时间预算对照（8 小时等时长比较） | 通用性（环境数少） |
| MLR-Bench（`2505.19955`） | 201 个 workshop 级研究任务 | 四阶段分解 + rubric 评审 | 评审者即 LLM 的可靠性 |
| TML-Bench（`2603.05764`） | 4 竞赛 × 3 预算 × 10 模型 × 5 次 | 显式报告 run-to-run 波动 | 跨任务泛化 |
| DSBench（`2409.07703`） | 466 分析 + 74 建模 | 真实数据分析任务 | 决策过程 |
| DSGym（`2601.16344`） | 统一执行环境 | 暴露"不读数据也能做对" | 长时程任务 |
| TimeSeriesGym（`2505.13291`） | 多来源时序挑战 | 拆出孤立能力（读仓库、代码翻译） | 端到端预算语义 |

**结论**：基准已经足够多，缺少的不是"又一个基准"，而是 **(a) 预算执行的可验证性、(b) 决策级指标、(c) 证据来源合法性**。`2602.22442` 的调研结论是：在它调查的 agentic AutoML 系统中，**没有任何一个报告结构化的决策级评估指标**。
