
# BS/UE 双 Agent 实验数据与仿真工具链调研

## 1. 文档目的

本文回答 BS/UE 双 Agent 模型评估与生命周期研究中的实验问题：

1. 到底需要哪些数据，哪些数据用于 Agent，哪些数据只能留给独立评价器。
2. 第一版是否必须有真实基站、真实 UE 和真实无线测量。
3. Sionna、QuaDRiGa、DeepMIMO、5G-LENA、ns-3 O-RAN、MATLAB、OAI、srsRAN 等工具各自适合解决什么问题。
4. 如何把链路级模型评估、网络级 KPI、模型生命周期和 Agent 工具调用接成一个可复现实验。
5. 从纯仿真到软件协议栈再到授权实测，应该怎样分阶段推进，避免一开始就陷入无法复现的复杂测试床。

本文服务于同目录下的：

- [端网协同候选方案](../设计草案/端网协同候选方案.md)
- [LCMAgent 相关论文综述与研究定位](./LCMAgent相关论文综述与研究定位.md)

本文讨论的是实验和证据设计，不把任何工具默认等同于真实网络，也不把射线追踪、系统级仿真、软件 RAN 和实测混写成同一类数据。

## 2. 先给结论

### 2.1 第一篇论文不需要一开始就做真实无线实测

如果论文的核心主张是：

> BS Agent 与 UE 本地 Runtime 能否在证据不完整、设备能力异构和模型版本变化时，减少错误发布、部分激活和回退失败？

那么第一版最需要的是**可交互的生命周期实验环境**，而不是立即采购完整 5G 测试床。

建议先完成：

```text
固定模型资产
    + 可控无线信道/CSI数据
    + 可注入设备与版本状态
    + 可执行的模型评估工具
    + 可改变状态的发布/回退模拟器
    + 独立隐藏评价器
```

这能够证明生命周期协同机制在明确假设下是否有效，但不能声称已经证明商用无线网络效果。

### 2.2 需要的不是一份 CSI 数据，而是一个完整实验回合

一个可评价的 Agent 样本应是一个 episode：

```text
初始状态
  -> Agent 可见证据
  -> 工具查询
  -> 工具返回结果
  -> 候选动作
  -> 本地验证/执行门
  -> 实际状态变化
  -> 运行监测
  -> 接受或回退
```

单独的 CSI 矩阵只能支持数值模型评估，不能支持以下主张：

- Agent 是否选择了正确的补测；
- BS 与 UE 是否形成一致状态；
- 发布是否会造成部分激活；
- 回退是否成功；
- 证据是否过期；
- LLM 是否比规则系统更有价值。

### 2.3 推荐的主路线

第一篇论文建议采用以下组合：

| 层次 | 推荐工具/数据 | 主要回答的问题 |
|---|---|---|
| 生命周期控制面 | Python 状态机、JSONL episode、固定模型卡、故障注入 | 双 Agent 的协同、权限、证据和回退机制是否有效 |
| CSI/链路级 | CsiNet 固定权重 + 作者数据；DeepMIMO 或 Sionna 生成扩展场景 | 模型误差、场景泛化、反馈开销和推理成本 |
| 动态信道 | QuaDRiGa 或 Sionna PHY | 移动性、时间相关信道、过期 CSI 和反馈延迟 |
| 网络级 | 5G-LENA；需要 O-RAN 逻辑时再接 ns-3 O-RAN | 吞吐量、时延、可靠性和资源变化 |
| 软件协议栈 | OAI RF simulator + FlexRIC，或 srsRAN 方案 | 工具、日志、模型调用和 RAN 软件集成 |
| 实测增强 | DeepSense 6G 或授权 SDR/OAI/srsRAN 测试床 | 仿真结果是否在真实测量条件下仍有意义 |

不要把所有工具同时作为主实验。第一版应指定一个主链路，其余工具用于交叉验证或后续增强。

## 3. 实验主张与证据等级

### 3.1 四类证据环境

| 环境 | 数据/环境 | 可以支持的主张 | 不能直接支持的主张 |
|---|---|---|---|
| D0 控制面夹具 | 合成模型卡、工具返回、状态机和故障注入 | 解析、工具调用、权限、预算、事务和回退逻辑 | 真实无线性能、真实射频鲁棒性 |
| D1 静态无线数据 | CSI、信道、射线追踪结果、已有日志 | 固定输入下的模型误差、兼容性和场景泛化 | 动作导致的因果后果、在线恢复 |
| D2 可交互无线仿真 | 动作会改变模型、反馈、资源或 KPI | 受控闭环、动态状态、补测和切换策略 | 商用网络效果、跨设备真实部署 |
| D3 软件 RAN/协议栈仿真 | OAI RF simulator、软件 UE/gNB、RIC 逻辑模块 | 软件集成、协议行为、日志、控制时序 | 真实天线、真实传播环境和现网稳定性 |
| D4 授权实测 | SDR、测试床、真实设备和独立测量 | 所测设备/场景的实测性能和实现成本 | 自动推广到其他设备、场景或运营商网络 |

证据等级不是质量排名，而是主张边界。一个高质量 D2 实验可以比一个没有隐藏真值、没有动作后果的低质量实测更能证明 Agent 机制；但 D2 不能被描述为真实无线部署验证。

### 3.2 仿真、重放、硬件在环和实测的区别

- **仿真**：传播、链路、网络或设备状态由模型生成。
- **重放**：使用历史日志或预生成数据，不一定允许新的动作改变环境。
- **硬件在环**：部分组件是真实硬件，环境或信道仍由仿真器提供。
- **实测**：传播和设备行为来自真实运行，仍需记录设备、频段、标定、地点、许可和测试条件。

“真实地图 + 仿真信道”是混合数据，不是完整实测；“真实日志重放”不等于新 Agent 动作已在真实网络执行；射线追踪生成的 CSI 也不能称作现场测量。

## 4. BS/UE 双 Agent 需要哪些数据

### 4.1 数据总表

| 数据组 | 典型字段 | 作用 | 是否给 Agent |
|---|---|---|---|
| 模型资产 | model_id、版本、权重哈希、架构、输入输出布局、量化、参数量 | 确认模型身份和可复现性 | 给摘要和受限字段 |
| 模型配对 | encoder/decoder、压缩率、反馈格式、维度、量化和协议版本 | 判断 BS/UE 是否可以共同使用 | 给结构化查询结果 |
| 模型证据 | 训练域、测试域、样本数、指标、限制、代码和权重来源 | 判断当前证据是否充分 | 给已授权证据 |
| 无线信道/CSI | 复数信道、时间、位置、频率、阵列、路径、噪声、场景 | 计算模型层和链路层指标 | 通常由数值工具访问 |
| 设备能力 | CPU、内存、加速器、功耗状态、模型支持、软件版本 | UE 本地可运行性检查 | UE 本地保留，上传摘要 |
| 链路状态 | SNR、CQI、MCS、BLER、HARQ、CSI-RS、反馈延迟、丢包 | 评价过期信息和业务后果 | 给工具和监测器 |
| 网络状态 | PRB、负载、队列、切片、用户数、切换、调度状态 | 评价全局收益和资源冲突 | BS Agent 可见摘要 |
| 动作日志 | 查询、补测、下载、安装、准备、激活、停用、回退 | 评价 Agent 轨迹和成本 | Agent 可见部分，评价器保留全量 |
| 状态变化 | 请求时间、真正生效时间、版本变化、失败原因、重试 | 评价事务一致性和证据新鲜度 | 工具返回摘要 |
| 运行后 KPI | 模型误差、吞吐、时延、可靠性、功耗、回退、恢复时间 | 判断是否接受发布 | 独立评价器保留真值 |
| 访问和隐私 | 授权范围、用途、保留期、脱敏、拒绝原因 | 评价数据治理和本地拒绝 | Agent 只能看到策略结果 |

### 4.2 模型资产数据

每个候选模型至少需要：

```json
{
  "model_id": "csi-encoder-a",
  "model_version": "1.0.0",
  "weight_sha256": "...",
  "role": "ue_encoder",
  "input_shape": [32, 32, 2],
  "output_shape": [128],
  "dtype": "float32",
  "quantization": "none",
  "required_memory_mb": 0,
  "supported_device_profiles": [],
  "supported_channel_profiles": [],
  "paired_models": [],
  "fallback_model_id": "csi-classic-v1"
}
```

这里的字段是实验记录建议，不是任何工具自带的统一格式。模型 ID、模型文件、输入输出契约和适用域必须分开记录。ID 相同不代表权重、归一化、量化或反馈布局一定相同。

### 4.3 CSI/信道数据

CSI 数据至少需要配套记录：

- 复数信道或实部/虚部表示；
- 子载波数、天线数、时域/频域布局；
- 采样时间和位置；
- 载频、带宽、采样率和 OFDM 参数；
- 发射/接收阵列几何、极化和天线顺序；
- 场景类型、LOS/NLOS、移动速度和轨迹；
- 噪声、估计误差、量化和反馈丢失；
- 归一化、域变换和预处理版本；
- 训练、验证、开发和最终测试划分。

如果使用旧 CsiNet 代码，不能只看 `.mat` 文件数量。代码中的 `HT`、`HF_all`、实虚部排列、归一化方式和子载波截取都属于模型输入契约；形状不一致时，结果不可直接比较。

### 4.4 Agent episode 数据

一个 episode 建议包含：

```text
episode_id
scenario_id
initial_state
visible_evidence
hidden_ground_truth
allowed_tools
budget
tool_calls[]
tool_results[]
candidate_actions[]
gate_decisions[]
actual_state_transitions[]
post_action_measurements[]
final_accept_or_rollback
```

其中 `hidden_ground_truth`、真正的故障原因、授权正确答案和最终留出测量不能进入 Agent 的提示、RAG 或工具返回。否则测到的是标签泄露，不是主动决策能力。

### 4.5 时序和成本数据

本项目不能只记录模型推理时间。至少要分开：

```text
观测产生时间
 -> 观测到达 BS/UE 时间
 -> Agent 开始决策时间
 -> 工具调用开始/结束时间
 -> 模型下载时间
 -> 本地准备时间
 -> 共同激活时间
 -> 业务 KPI 生效时间
```

还要记录：

- 工具调用次数；
- 每次补测的数据量；
- 计算和存储成本；
- UE 能耗或功耗代理指标；
- API/模型调用费用；
- 失败、重试和超时；
- 证据有效期和过期时间。

如果仿真在等待 LLM API 时被冻结，却把证据年龄视为没有增加，会高估系统能力。

### 5.2 公开无线模型/数据资源

#### CsiNet 及相关 CSI 模型仓库

CsiNet 类仓库适合做第一版固定模型基线，因为有模型结构、预训练权重和 only-test 代码。它可以提供：

- 编码器/解码器模型；
- 固定压缩率；
- NMSE、相关性或 GCS 等模型层指标；
- 室内/室外等已有划分。

但它通常不能直接提供：

- 真实 UE/gNB 运行时；
- 反馈链路中的丢包、延迟和调度；
- 设备功耗；
- 模型发布、切换和回退事务。

因此 CsiNet 适合作为数值模型，不是完整端网实验环境。

#### DeepMIMO

DeepMIMO 的定位是把射线追踪场景转化为可复用、可配置的无线数据集。适合：

- 场景间泛化；
- 不同用户位置和天线配置；
- CSI、波束和路径相关学习；
- 训练域/测试域分离；
- 复现实验的参数化数据生成。

不适合直接承担：

- 动作改变后的网络闭环；
- 真实 UE 功耗和推理时延；
- 完整 O-RAN 控制流程；
- 未经额外处理的实时移动轨迹。

DeepMIMO 应被理解为“由射线追踪结果生成的场景化数据接口”，而不是现场测量数据。使用时必须记录场景版本、射线追踪来源、用户区域、天线、频率、采样和数据生成参数。

#### DeepSense 6G

DeepSense 6G 适合补充真实感知/通信多模态数据，例如位置、视觉、LiDAR、雷达或波束相关观测，具体以场景数据卡为准。它可以增强：

- 仿真到现实的比较；
- 多模态状态感知；
- 位置/环境与无线表现的关联；
- 预测与测量的差异分析。

它不应被默认称为完整 CSI、完整 NR 日志或可随意干预的数字孪生。每个场景的模态、坐标系、采集条件和访问许可必须单独核对。

#### WirelessBench、TeleLogs 和 TeleLogsAgent

这些资源更适合 Agent 控制面，而不是无线物理层：

- WirelessBench：无线任务、工具调用和多步决策基准种子；
- TeleLogs：网络运维或根因分析相关日志数据；
- TeleLogsAgent：工具交互和运维 Agent 评价候选。

它们可以帮助构造 Agent 的任务和工具接口，但不能替代 CSI、信道、设备能力和业务 KPI。

## 6. 工具链比较

### 6.1 Sionna

#### 定位

Sionna 当前本地 README 将其分成三个主要部分：

- Sionna RT：无线传播射线追踪；
- Sionna PHY：链路级无线通信仿真；
- Sionna SYS：基于物理层抽象的系统级仿真。

这使 Sionna 很适合做从传播/信道、物理层到部分系统级的连续实验，也适合与深度学习模型和 PyTorch 工作流结合。

#### 对本项目的价值

- 产生或处理 CSI、路径和传播结果；
- 评价编码、调制、信道编码、检测和链路指标；
- 研究 CSI 过期、噪声、反馈延迟和丢失；
- 将无线仿真与神经模型放在同一 Python 实验流水线中；
- 为 Agent 提供可交互的评估工具。

#### 限制

- 不自动提供模型注册表、版本事务和 Agent；
- 不自动提供完整真实 O-RAN 控制栈；
- RT 场景的几何、材料和标定质量会影响结论；
- PHY、SYS 和 RT 的输入输出不能默认直接拼接；
- 软件版本、GPU、CUDA、PyTorch 和场景文件必须固定。

#### 适合的实验

```text
Agent 选择测试场景/反馈策略
  -> Sionna PHY/RT 工具执行
  -> 返回 NMSE、BLER、吞吐、时延和资源摘要
  -> UE Runtime 检查本地预算
  -> Agent 选择继续、切换或回退
```

### 6.2 QuaDRiGa

#### 定位

QuaDRiGa 是几何基础的随机信道建模工具，适合生成具有空间、时间、频率相关性的无线信道，尤其适合研究移动性、轨迹、阵列和多用户信道变化。

#### 对本项目的价值

- 生成时间相关 CSI；
- 模拟移动 UE、速度和轨迹；
- 研究 CSI 过期、预测失败和反馈时延；
- 比单纯独立随机样本更接近连续运动中的信道变化；
- 构造不同场景和参数下的鲁棒性测试。

#### 限制

- 它不是完整 PHY 链路仿真器；
- 它不是网络级调度器或 O-RAN 仿真器；
- 它不包含模型发布、设备资源和 Agent 事务；
- 随机信道仍是模型生成，不是实测传播；
- 需要将信道输出接到自己的 PHY、CSI 编解码或系统级仿真器。

#### 与 DeepMIMO 的差异

| 维度 | QuaDRiGa | DeepMIMO |
|---|---|---|
| 主要角色 | 参数化/时间相关信道模型 | 射线追踪场景到数据集的生成接口 |
| 强项 | 移动性、空间/时间相关性、随机化 | 场景化、用户位置、射线追踪数据和 ML 数据组织 |
| 典型数据 | 连续轨迹上的信道系数 | 指定场景和配置下的信道/路径样本 |
| 适合研究 | 过期、预测、反馈时序和动态鲁棒性 | 场景泛化、空间划分和固定模型评估 |
| 不能替代 | 真实测量和完整链路 | 真实测量和在线环境 |

第一版不需要同时使用 QuaDRiGa 和 DeepMIMO。若研究重点是模型发布和事务，先用 DeepMIMO 或固定 CsiNet 数据；若研究重点是 CSI 时效和反馈控制，再加入 QuaDRiGa。

### 6.3 DeepMIMO

DeepMIMO 适合把场景、用户区域、阵列、频率和采样参数变成可重复的数据生成流程。它是当前最适合第一版 CSI 场景扩展的工具之一，但必须注意：

- 场景生成参数决定数据分布；
- 空间相邻点不能随机分到训练和测试两侧；
- 同一射线追踪场景的不同设置可能并不构成真正独立的测试环境；
- 预生成数据不能自动重算 Agent 动作后的网络状态；
- 使用它不能直接声称真实设备泛化。

建议按**场景区域或轨迹组**划分，而不是按单个 CSI 样本随机切分。

### 6.4 MATLAB 5G Toolbox 和 Wireless Toolbox

MATLAB 工具链适合做标准参数、NR 波形、信道、链路级和系统级的快速验证，尤其适用于：

- 3GPP NR 波形和参数；
- TDL/CDL 等信道模型；
- CSI-RS、反馈和链路流程原型；
- 参考实现和结果交叉检查；
- 与既有 MATLAB 无线算法代码衔接。

限制是：

- 商业许可和版本依赖；
- Agent、模型注册和端网事务仍需自己实现；
- 不应把工具箱生成结果直接称作实测；
- MATLAB 与 Python、Sionna、ns-3 之间需要明确接口和单位转换。

如果团队已经有 MATLAB 代码，它适合作为参考实现或交叉验证工具；如果希望全部实验开源和自动化，Sionna/Python 链路更容易形成可复现实验包。

### 6.5 5G-LENA

5G-LENA 是基于 ns-3 的 NR 系统级仿真模块，适合评价：

- 小区和多 UE；
- 调度、负载、移动性和资源分配；
- 吞吐量、时延、丢包、可靠性和业务 KPI；
- 网络侧策略对业务结果的影响。

它不适合直接承担：

- 高保真的神经 CSI 编解码模型；
- 复杂射线追踪传播细节；
- 真实 UE 端推理功耗；
- 完整 O-RAN 商用接口。

5G-LENA 最适合作为 Sionna/DeepMIMO/CsiNet 输出之后的系统级验证层。需要自己定义模型动作如何影响 CSI、反馈开销、链路预算或调度状态。

### 6.6 ns-3 O-RAN 模块

本地 `ns3-oran` README 显示，它提供了 Near-RT RIC 模型、报告和命令仓库、Logic Module、冲突缓解 API、节点报告、组件激活/停用，以及 ONNX Runtime/PyTorch 集成等功能。

对本项目的价值：

- 模拟网络侧 Agent 或 xApp 的调用位置；
- 记录报告、命令、逻辑模块和冲突处理；
- 研究网络侧模型或配置动作如何影响后续状态；
- 把模型生命周期控制面接入网络级仿真。

限制：

- 功能建模不等于真实 E2 协议实现；
- README 中的示例不能自动推断为完整 5G NR O-RAN 支持；
- 与 5G-LENA、ns-3 版本、PyTorch 和 ONNX Runtime 有依赖；
- UE 本地 Runtime 和模型配对事务仍需自行扩展。

如果论文核心是“端网模型生命周期 Agent”，ns-3 O-RAN 可以作为网络控制层，但不能单独作为完整的无线数据来源。

### 6.7 OpenAirInterface（OAI）

OAI 是软件 RAN 栈，支持 4G/5G 研究、仿真、原型和 COTS 硬件部署。其仓库包含 gNB、UE、协议栈、RF simulator 和 E2 相关代码路径。

对本项目的价值：

- 软件 UE/gNB 行为和日志；
- RF simulator 下的端到端协议集成；
- 真实接口、配置、启动、停止和故障记录；
- 后续接 SDR 做硬件在环或授权实测；
- 验证 Agent 不在时隙级实时路径上时，能否安全参与慢速管理。

限制：

- 构建和配置成本高；
- 版本、内核、网卡、USRP、射频前端和核心网依赖明显；
- RF simulator 不是现场无线传播；
- 运行日志和软件行为不等于真实射频性能；
- 模型发布和 CSI 神经编解码接口需要自行接入。

OAI 更适合第二阶段或第三阶段，不建议作为第一步的唯一实验环境。

### 6.8 srsRAN

srsRAN 适合构建开放软件 RAN、软件 UE/gNB 和 SDR/仿真相关实验。它与 OAI 类似，可以提供软件协议栈和硬件在环路径，但具体功能、版本和设备支持必须以当前官方文档为准。

它适合的研究问题：

- 软件 RAN 侧的模型部署和控制接口；
- UE/gNB 版本不一致和配置变更；
- 端到端吞吐、时延和连接稳定性；
- 与 SDR 的硬件在环测试。

它不自动解决：

- CSI 神经模型的训练和部署；
- BS/UE 双 Agent 协议；
- 模型证据和回退评价；
- 实际运营商网络数据获取。

OAI 和 srsRAN 不建议在第一篇论文中同时做主平台。应根据团队熟悉度、设备和已有代码选择一个。

### 6.9 FlexRIC 和 O-RAN 软件集成

FlexRIC、ns-3 O-RAN 和 OAI 组合适合做 RIC/xApp 或网络控制面的实验，但它们的接口、版本和运行方式不是同一个统一平台。使用时需要固定：

- ns-3 或 OAI 版本；
- E2/RIC 适配方式；
- 报告和控制动作的字段；
- xApp/rApp 的调用时序；
- 统计指标和时间戳；
- 失败、重试和组件重启方式。

不要因为仓库名称中有 O-RAN 就直接写成“标准 O-RAN 测试床”。需要说明是仿真模型、软件栈集成还是硬件测试。

## 7. 推荐工具组合

### 7.1 组合 A：最快的第一版论文

```text
固定 CsiNet/其他 CSI 模型
  + 作者匹配数据或 DeepMIMO
  + Python 生命周期仿真器
  + BS LLM Agent
  + UE 确定性 Runtime
  + 故障注入和独立评价器
```

适合证明：

- 证据驱动补测；
- 模型配对；
- 共同激活和回退；
- 单 BS Agent 与双侧 Runtime 的差异。

不适合声称：真实无线网络收益、真实设备功耗或现网部署。

### 7.2 组合 B：CSI 链路级论文

```text
DeepMIMO 或 QuaDRiGa
  + Sionna PHY 或 MATLAB 5G Toolbox
  + CsiNet/TransNet/其他固定模型
  + CSI-RS/反馈/丢失/延迟模拟
  + BS-UE 生命周期控制器
```

适合证明：

- 场景泛化；
- CSI 过期和反馈延迟；
- 误差、反馈开销、BLER、吞吐和时延之间的权衡；
- 模型切换和回退的业务代价。

要求：不能只报告 NMSE，必须建立 CSI 模型输出到通信 KPI 的映射。

### 7.3 组合 C：网络级 O-RAN 论文

```text
5G-LENA
  + ns-3 O-RAN 或自定义 RIC 逻辑
  + Python/LLM Agent 作为慢速控制器
  + UE/BS 模型状态和动作日志
  + 网络负载、切换、资源和业务 KPI
```

适合证明：

- 多 UE 和多小区下的全局/本地信息冲突；
- 模型或控制策略切换对网络 KPI 的影响；
- 网络侧 Agent 的工具调用、资源和动作安全。

要求：需要明确无线模型如何嵌入系统级仿真；不能只在 ns-3 中运行一个独立的文本 Agent，然后把网络仿真结果当作 Agent 贡献。

### 7.4 组合 D：软件 RAN/硬件在环论文

```text
OAI 或 srsRAN
  + RF simulator 或 SDR
  + FlexRIC/自定义控制接口
  + UE Runtime
  + 真实软件日志和设备资源监测
```

适合证明：

- 端网模型控制流程能否接入软件 RAN；
- 模型准备、激活、回退和日志追踪是否可执行；
- 实际软件时延、CPU、内存和失败模式。

成本和风险最高，适合在控制面仿真稳定后做增强，不应一开始就把它作为唯一成功条件。

### 7.5 组合 E：真实测量增强

```text
DeepSense 6G 或授权测量数据
  + 固定模型和独立评价器
  + 仿真/实测域差异分析
  + 设备或 SDR 运行成本测量
```

适合证明：

- 仿真域和真实观测之间的差异；
- 证据驱动补测在真实数据缺口下是否有用；
- 模型适用条件和数据治理是否需要本地化。

真实测量数据必须标注采集条件、许可、设备、场景、坐标系、时间戳和可公开范围。

## 8. 仿真工具之间如何衔接

### 8.1 推荐的分层接口

不要让 Agent 直接读写各仿真器内部对象。定义统一的实验工具接口：

```text
generate_channel(config)
evaluate_model(model_ref, data_ref, device_profile)
simulate_link(link_config, model_ref, channel_ref)
simulate_system(system_config, policy_ref, scenario_ref)
read_runtime_state(node_ref)
prepare_model(node_ref, model_ref)
activate_pair(bs_model_ref, ue_model_ref)
rollback_pair(target_pair_ref)
```

每个工具返回：

```json
{
  "tool_call_id": "tool-001",
  "status": "success",
  "source_type": "simulation",
  "simulator": "sionna-phy",
  "simulator_version": "pinned",
  "config_hash": "...",
  "input_refs": [],
  "output_refs": [],
  "metrics": {},
  "start_time": "...",
  "end_time": "...",
  "sim_time": {},
  "failure_reason": null
}
```

### 8.2 统一数据对象

建议定义以下对象，而不是把所有结果转成自然语言：

- `ChannelSnapshot`：某时刻或轨迹片段的信道和场景引用。
- `ModelArtifact`：权重、架构、哈希和依赖。
- `CompatibilityReport`：输入输出、版本、维度和配对检查。
- `EvaluationReport`：模型、链路、系统、资源和时延指标。
- `RuntimeState`：设备能力、当前版本、资源余量和本地策略。
- `EvidenceItem`：来源、时间、有效期、权限和可信级别。
- `ActionProposal`：候选动作、目标、成本、前置条件和回退目标。
- `ActivationEvent`：请求、准备、激活、失败和实际生效状态。

### 8.3 仿真时间和墙钟时间

必须同时记录：

- `sim_time`：无线环境中的时间；
- `wall_time`：实际运行时间；
- `measurement_time`：测量产生时间；
- `arrival_time`：证据到达 Agent 的时间；
- `effective_time`：动作真正生效时间。

LLM 调用期间，无线环境是否继续变化，应由实验配置明确。若暂停环境，报告为“冻结仿真”；若继续变化，必须更新证据有效性。

## 9. 第一版需要的数据量和划分

### 9.1 不先追求大数据量

本项目第一篇论文的核心不是训练一个更大的无线模型，而是验证生命周期决策。因此，优先保证：

- 场景和设备配置覆盖足够；
- 故障注入覆盖清楚；
- episode 数量可以支持置信区间；
- 训练/开发/测试严格隔离；
- 每个错误动作都有可解释原因；
- 基线使用相同数据、工具和预算。

比起大量随机 CSI，少量但结构清晰的场景和完整动作轨迹更有价值。

### 9.2 建议的数据划分

按以下单位切分，而不是随机切单个样本：

- 场景区域；
- 移动轨迹；
- 设备配置；
- 模型版本组；
- 故障类型；
- 工具错误模板；
- 时间窗口。

同一射线追踪场景的空间邻近点不能同时进入训练和最终测试；同一故障模板的轻微改写不能同时进入开发和测试；同一模型权重的重复报告不能伪装成独立样本。

### 9.3 推荐的最小 episode 组成

每种关键故障至少应有：

- 正常发布；
- 证据缺失；
- 证据过期；
- UE 能力不足；
- 版本不匹配；
- 数据权限拒绝；
- 下载或准备失败；
- 单侧激活成功、另一侧失败；
- 激活后业务 KPI 退化；
- Agent 或工具超时。

每类故障应改变初始观测、预算或时序，而不是简单复制同一条模板。

## 10. 需要测什么指标

### 10.1 Agent/生命周期指标

- 正确发布率；
- 错误发布率；
- Unsafe APPLY Rate；
- 版本不匹配率；
- 单侧激活率；
- 回退成功率；
- 恢复时间；
- 过期证据使用率；
- UE 本地拒绝率；
- 不必要补测率；
- 每个 episode 的工具调用次数和数据量。

### 10.2 无线模型指标

- NMSE；
- GCS 或相关性；
- BER/BLER；
- CSI 反馈比特数和空口开销；
- 反馈延迟和信息年龄；
- 模型推理时延；
- 参数量、内存和计算量；
- 场景外泛化。

### 10.3 系统和设备指标

- 吞吐量；
- 业务时延；
- 可靠性/违约率；
- PRB 或其他无线资源使用；
- UE CPU、内存和功耗；
- BS 计算和存储；
- 模型下载量；
- 业务中断时间；
- 切换期间性能损失。

NMSE 不是吞吐量，CSI 重构误差也不是自动的端到端业务收益。若论文声称“系统收益”，必须有从模型输出到链路/系统 KPI 的可执行映射。

## 11. 基线和消融

### 11.1 最低基线

| 基线 | BS | UE | 作用 |
|---|---|---|---|
| B0 | 固定规则/传统策略 | 传统本地检查 | 非 Agent 基线 |
| B1 | 单 BS Agent | 被动执行 | 检验 UE 本地组件是否必要 |
| B2 | BS Agent | 确定性 Runtime | 推荐主方案 |
| B3 | BS Agent | 轻量 UE Agent | 检验 UE 侧规划是否有额外价值 |
| B4 | 全知 Oracle | 全知 | 估计上限，不作为可部署方案 |

所有基线必须使用相同的：

- 候选模型；
- 初始观测；
- 工具集合；
- 数据预算；
- 发布窗口；
- 回退机制；
- 最终评价器。

### 11.2 关键消融

1. 去掉 UE 本地能力检查。
2. 去掉模型配对检查。
3. 去掉证据时间戳和过期判断。
4. 去掉主动补测，改为固定测试序列。
5. 去掉在线运行后验收。
6. 去掉确定性执行门，只使用 Agent 输出。
7. 去掉回退控制器。
8. 让 UE 使用完整 LLM，测量额外收益与成本。
9. 只看 NMSE，不看业务 KPI，作为不完整评价对照。
10. 用第二个无线用例替换 CSI，检验架构是否具备可迁移性。

## 12. 推荐的四阶段实施路线

### Phase 0：生命周期控制面原型

**目标**：先证明 Agent 机制，而不是证明无线模型。

工具：

- Python；
- JSONL episode；
- 固定模型卡；
- 合成评估报告；
- 状态机和故障注入；
- BS Agent；
- UE Runtime；
- 独立评价器。

必须完成：

- 共同准备/激活/回退；
- 版本不匹配；
- UE 本地拒绝；
- 证据过期；
- 工具失败和重试；
- 统一指标和日志。

产出：可以回答“是否有双侧生命周期机制价值”，但不能回答“无线模型是否提升链路性能”。

### Phase 1：固定 CSI 模型和静态场景

推荐：

- CsiNet 或其他已有固定模型；
- 作者匹配测试数据；
- DeepMIMO 场景扩展；
- Python 数值评估工具。

必须验证：

- 模型和数据输入契约；
- 权重哈希和版本；
- 训练域/测试域划分；
- NMSE、相关性、反馈开销和推理时间；
- BS/UE 模型配对；
- 资源不足和版本切换。

### Phase 2：动态信道和链路级评价

选择一个：

- QuaDRiGa：优先研究移动性、时间相关性和过期 CSI；
- Sionna PHY：优先研究链路、反馈、噪声、丢失和端到端物理层；
- MATLAB 5G Toolbox：优先快速实现标准 NR 参考流程和交叉验证。

不要第一版同时使用三个链路工具作为主结果。可将一个作为主平台，其余作为 sanity check 或扩展实验。

### Phase 3：系统级和软件 RAN 集成

两条路线择一：

#### 路线 A：5G-LENA + ns-3 O-RAN

优点：

- 可重复；
- 适合多 UE/多小区；
- 便于测吞吐、时延、资源和切换；
- 可接逻辑模块和 RIC 记录。

缺点：

- 需要自己把模型输出映射到系统级行为；
- 不能直接当作完整真实 O-RAN；
- CSI 神经编解码的物理层细节不完整。

#### 路线 B：OAI RF simulator + FlexRIC

优点：

- 更接近软件 RAN 和协议栈；
- 可以产生真实软件日志、配置和控制时序；
- 便于后续接 SDR。

缺点：

- 构建、配置和版本成本较高；
- 对机器、内核、网络接口和组件兼容性要求高；
- RF simulator 不是真实传播；
- 需要额外开发模型和生命周期接口。

### Phase 4：授权实测或硬件在环

可选方式：

- DeepSense 等公开实测数据；
- OAI/srsRAN + SDR；
- COTS UE/gNB 测试床；
- 现有实验室 RAN 平台。

这一阶段主要验证：

- 实际推理和加载成本；
- 软件栈日志和动作生效时序；
- 真实设备资源和功耗；
- 仿真域到实测域的偏差。

没有实测时，论文可以诚实地写成“仿真和软件协议栈验证”；不能写成“真实网络部署验证”。

## 13. 哪条路线最适合当前项目

### 13.1 推荐主路线

当前项目最稳妥的主路线是：

```text
Phase 0 控制面
  -> Phase 1 CsiNet + 作者数据/DeepMIMO
  -> Phase 2 Sionna PHY 或 QuaDRiGa 二选一
  -> Phase 3 5G-LENA + ns-3 O-RAN 或 OAI RFsim 二选一
```

推荐优先顺序：

1. **先做生命周期控制面，不等待真实 CSI 数据。**
2. **再接固定 CSI 模型和可验证数据。**
3. **如果研究的是过期和反馈时序，选 QuaDRiGa；如果研究链路效果，选 Sionna PHY。**
4. **如果研究多 UE/网络 KPI，选 5G-LENA；如果研究软件 RAN 集成，选 OAI RFsim。**
5. **实测作为增强证据，不作为第一阶段阻塞条件。**

### 13.2 不推荐的路线

不推荐一开始同时做：

- Sionna RT；
- Sionna PHY；
- QuaDRiGa；
- DeepMIMO；
- MATLAB；
- 5G-LENA；
- ns-3 O-RAN；
- OAI；
- srsRAN；
- FlexRIC；
- 真实 SDR。

这会把研究变成平台集成项目，无法判断哪一部分产生了收益。工具越多不等于证据越强，反而会增加版本、单位、时间和数据格式不一致的风险。

## 14. 主要风险和数据质量检查

### 14.1 标签泄露

答案、故障真因、目标测试结果、正确发布动作和回退标签不能进入 Agent 的提示或检索库。按字段权限切分，不要只按文件切分。

### 14.2 空间泄露

同一射线追踪场景的相邻位置如果分到训练和测试两侧，可能高估泛化。按场景区域、轨迹和时间组划分。

### 14.3 模型输入不一致

检查：

- 实部/虚部顺序；
- 天线和子载波顺序；
- 归一化；
- DFT/角域变换；
- 反馈维度；
- 量化；
- 训练和推理框架；
- 数据单位。

### 14.4 时间冻结

仿真等待 Agent/API 时，环境是否继续变化必须明确。否则会错误地把长推理时间当作零时延。

### 14.5 仿真器自洽性

如果信道由某个工具生成，再由同一工具或同一模型计算结果，实验只能证明该仿真体系内部自洽。应至少增加：

- 不同场景参数；
- 不同信道模型；
- 时间/空间留出；
- 噪声和反馈丢失；
- 另一个实现或实测数据的小规模交叉验证。

### 14.6 许可证和数据授权

代码开源不等于数据、权重和场景文件可以任意再分发。需要登记：

- 软件许可证；
- 数据访问条件；
- 权重许可；
- 实测数据使用范围；
- 是否允许公开发布样本；
- 是否允许上传给外部 LLM/API。

## 16. 最终建议

### 16.1 数据层面的最小闭环

第一版论文至少需要完成：

```text
固定模型资产
  -> 可复现 CSI/信道数据
  -> 模型评估报告
  -> BS/UE 兼容性和资源状态
  -> Agent 补测/切换动作
  -> 状态变化和失败注入
  -> 独立验收与回退指标
```

### 16.2 工具层面的最小闭环

优先实现：

1. Python 生命周期状态机。
2. CsiNet 或其他固定 CSI 模型的 only-test 评估。
3. DeepMIMO 或作者数据的严格场景划分。
4. Sionna PHY 或 QuaDRiGa 二选一。
5. 一个独立的模型兼容性和设备资源检查器。
6. 一个可注入失败、延迟和过期证据的发布模拟器。

### 16.3 论文表述边界

如果没有真实 RF 或硬件在环，只能说：

- 在可控无线仿真中验证；
- 在指定数据和模型配置下验证；
- 在软件 RAN/RF simulator 中验证；
- 证明生命周期机制在实验环境内有效。

不能说：

- 已证明适用于商用网络；
- 已证明适用于所有 UE；
- 已证明降低真实网络功耗；
- 已完成真实 O-RAN 部署；
- 仿真 CSI 就等于真实现场 CSI。

## 18. 结论

对于 BS/UE 双 Agent 论文，实验数据的核心不是“找一个最大的无线数据集”，而是构造一个能够同时连接以下对象的可复现实验闭环：

```text
无线状态
  + 模型资产
  + 端侧资源和隐私事实
  + Agent 工具调用
  + 模型准备/激活/回退动作
  + 动作后无线和业务 KPI
  + 独立隐藏评价
```

当前最推荐的工具路线是：

```text
Python 生命周期仿真
  + CsiNet 固定模型
  + 作者数据或 DeepMIMO
  + Sionna PHY 或 QuaDRiGa（二选一）
  + 后续再接 5G-LENA/ns-3 O-RAN 或 OAI RF simulator
```

Sionna、QuaDRiGa、DeepMIMO、5G-LENA 和 OAI/srsRAN 不是互相替代的工具，而是分别位于传播/信道、链路、系统、软件 RAN 和实测层。第一篇论文应选择一个主平台，明确每个结果能够支持的主张，保留其他工具作为扩展或交叉验证。
