### 22.9 在真实研究平台里怎样组合成熟做法：九层可落地设计

```text
┌────────────────────────────────────────────────────────────┐
│ Research Brief: question, non-goals, resources, provenance  │
└──────────────────────┬─────────────────────────────────────┘
                       ↓
        1. Literature & Prior-Result Grounding
                       ↓
        2. Hypothesis Pool / Novelty Checks
                       ↓
        3. Search Scheduler (BO / TPE / Tree / Islands / Agent)
                       ↓
        4. Isolated Candidate Workspace (branch/container)
                       ↓
        5. Frozen Experimental Contract / Read-only Grader
                       ↓
        6. Execution / Early Reject / Replication / Holdout
                       ↓
        7. Evidence Audit (correctness, leak, reward hacking)
                       ↓
        8. Append-only Experiment DAG + Decision & Claim Ledger
                       ↓
        9. PI Judgment / Human Review / Publication Gate
                       ↺ next verified hypothesis
```

**工程最低协议（建议，不是现有项目统一 API）**：

```yaml
campaign:
  goal: "improve validation quality while preserving correctness"
  immutable_contract_hash: "sha256:..."
  max_gpu_hours: 40
  max_llm_usd: 100
  max_experiments: 200
  editable_paths: ["src/model/**", "configs/**"]
  forbidden_paths: ["evaluation/**", "datasets/holdout/**"]
  stop_on_budget_exceeded: true
experiment:
  hypothesis_id: "H-023"
  parent_commit: "..."
  candidate_commit: "..."
  evaluation_version: "v1"
  seeds: [11, 22, 33]
  metric: "loss"
  additional_metrics: ["latency", "memory", "calibration"]
  correctness_gate: "tests + oracle checks"
  decision: "keep|discard|retry|inconclusive"
  evidence: ["stdout", "stderr", "config", "diff", "evaluation.json"]
  audit: ["data_leak", "score_access", "metric_reproducibility"]
```

设计要点：

1. **控制面与数据面分离**：LLM 可写候选代码，但不可写隐藏 grader、参考标签和预算计数器。Git 路径 `off_limits` 仅仅是提示/记录，不等于独立安全边界。
2. **短试验筛选，长试验认证**：先低资源 proxy 指标淘汰，再多种子复验；当方法有真实理论价值但短预算分数平时，允许人审的“探索基金”。
3. **三个指标面板**：业务 KPI（loss/latency/quality）、实验质量（可信改进率/作弊率）、科研能力（novelty、引用可核验度、迁移、成本）。
4. **共享经验但保留来源链**：记忆中保存`学到什么`、`在哪个版本/哪些数据上成立`、`有什么反证`、`何时失效`，而非只存“这招很棒”。
5. **统计控制**：比较多个自适应候选时，单次 validation 改进易遭 winner's curse；建议保留只用一次的锁定 final holdout，并报告 bootstrap/配对多种子 CI。
6. **安全与合规**：生成代码在隔离环境运行、依赖固定 hash、禁用自动外传数据、对高风险数据/算力耗费使用人工批准。

### 22.10 可以直接开展的五组科研比较试验

#### 试验 I：AutoML vs Agent for AutoML vs 典型 autoresearch

**任务集**：3 个公开 tabular ML（不同特征规模）、2 个神经训练 recipe、1 个程序性能任务。比较：Optuna TPE、BOHB、FLAML、AutoGluon、AIDE-style code search、oh-my-pi、pi-autoresearch、SwarmResearch-style harness。**不是要求每个框架都能做所有任务**；对不适用项目先界定 capability coverage，再在交集任务作同资源比对。

**控制变量**：硬件、wall-clock、GPU-hours、LLM tokens、实验次数、训练数据版本、验证协议、执行沙箱、独立 final holdout、种子数量、公开/隐藏数据访问。报告最佳值的同时绘制 time-to-first-valid-improvement、quality-vs-cost、valid-improvement rate 和 P(reward hack)。

#### 试验 II：单 Agent、树搜索、岛屿、共享 Git DAG

对照 `greedy → tree → 4 islands → 4 islands + shared verified memory`。衡量独立假设覆盖率、重复实验率、创新方法的专家盲评、新方向出现率、每单位算力改进。借鉴 FML-Bench、SwarmResearch、Agora、Heuresis 的设计思想。[A13][A14][A18][A20]

#### 试验 III：研究记忆消融

对照 `无记忆 / 最新运行摘要 / 累积失败日志 / 假设-证据图 / 含反证与适用条件的验证记忆`，在上下文刷新与长周期运行中评测。重点检查记忆污染、错误的正向迁移和基于历史失败的过早剪枝。

#### 试验 IV：质量门控防作弊

对照 `自评 / 交叉模型 reviewer / 只读 frozen grader / hidden set / frozen grader + hidden set + 多种子`。需在合规隔离的公开模拟基准执行；不能将审核成功率和指标提升率混为一谈。可借鉴 Nick Oak 失败案例、Reward Hacking 论文与 ARIS 的证据门。[A07][A23][A35]

#### 试验 V：人类科研判断能力

引入 SciΠvot 的关键决策，比较 `LLM 自动决策 / 不看历史的第二 Agent 审批 / Research Wiki 增强 / 专家抽查`。成本—质量指标：纠正错误决策数、错杀研究方向数、后续预算浪费、被验证的研究结论比率。[A30]

### 22.11 何时部署哪一种？

| 使用条件 | 推荐起点 | 不建议的捷径 |
|---|---|---|
| 标准表格建模、明确指标、预算有限 | AutoGluon/FLAML/Optuna + 版本化评估 | 让 LLM 直接重写整个评测器 |
| 优化代码性能/模型训练速度 | pi-autoresearch / oh-my-pi + frozen benchmark + correctness gates | 单次运行提速即合并 |
| 开放式模型架构/算法探索 | Agent code search + TPE/BO + 分支式研究记忆 | 只追逐验证集最佳值 |
| 文献→科研假设→实验→论文 | ARIS/AutoResearchClaw/NanoResearch + 独立验证 | 把生成 PDF 视为研究完成 |
| 多人/多 Agent 长期研究 | Agora/CORAL/SwarmResearch | 让多个 Agent 不隔离地共用 score file |
| 研究 Agent 自我改进 | AIDE² 式独立外层基准 + held-out 套件 | 同一任务兼作训练与成功证明 |
| 需要可靠性评价/论文课题 | FML-Bench + AutoResearchEval + SciΠvot + Into the Unknown | 用一个公开 leaderboard 代表科学发现能力 |

### 22.12 可验证的新研究问题（重点推荐）

1. **Research-conditional AutoML**：根据阶段、预算与先前实验密度，动态选择 TPE / MAP-Elites / agent tree search，而不是固定一种搜索器；检验 FML-Bench 所发现的改进机会结构。[A20]
2. **Verifiable long-horizon memory**：设计记录依赖条件、反证和有效期的 Git DAG / knowledge graph，度量相对于无记忆的长期有效进展。[A14]
3. **Cost-aware meta-research**：让 outer loop 学习如何分配短实验、复验和探索新方向的预算，避免 expensive evaluator 将优化收益吃掉。[A15][A24]
4. **Anti-reward-hacking benchmark design**：原样复测优化后候选，组合 private metric、独立复算和审计器，度量被欺骗概率而非只报最高分。[A23][A35]
5. **Scientific judgment Agent**：以 SciΠvot 为基础训练/评估“终止一个方向或改实验协议”的判断力，区分方向判断与代码能力。[A30]
6. **Dual discovery objectives**：同时优化预测指标和原创度、可靠性，研究 Novelty-Quality Pareto frontier，而非简单 scalarize 所有东西。[A18]
7. **Self-improving AutoML orchestration**：保留经典 AutoML engine，只递归优化 Agent 调度/异常诊断/harness，使用未见任务验证元改进。[A21]

### 22.15 本章最后判断：autoresearch 的研究前沿在哪里？

**新的核心问题不是“能否让 Agent 通宵不停写代码”，而是“能否让一个研究组织在固定资源下持续产出值得信任、可审计、可迁移、具有新颖性的发现”。**

- 如果只是追求明确、廉价且可验证的性能指标，**传统 AutoML、优化器和通用实验循环仍是强基线**。
- 如果研究对象包括模型代码、评测策略与长周期计划，**Agent for AutoML 和 autoresearch 的边界会大量重叠**，单 Agent 的性能不应被误当成搜索器的纯收益。
- 如果研究成果需要科学主张，必须增加**独立评估与证明义务**：评估器不可被候选修改，保存原始结果与反证，严格区分可行性试验与最终 holdout，保留人类关键判断。
- 2026 年更值得研究的技术组合是：`经典 AutoML/HPO + 可执行 Agent 研究计划 + 群体搜索记忆 + 冻结评估器 + 证据/科学判断审计 + 必要时的外层 harness 改进`。

**因此[第 21 章](概念边界与详细对照.md#s21)的“autoresearch 将程序作为候选”是早期常见模式的局部描述；本章对其修正为“把整个研究过程——候选、实验、证据、检验规则、记忆与研究策略——作为可编排、可质询的闭环”，其中哪些对象可被 Agent 修改、哪些必须锁定，是研究系统可靠性的首要设计问题。**
