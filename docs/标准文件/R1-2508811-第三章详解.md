# R1-2508811 第三章详解：AI/ML 框架与评估

## 1. 章节定位

本章对应 PDF 第 50-57 页，标题为 **Framework and evaluation（框架与评估）**。它没有继续讨论某一个具体空口用例，而是试图回答 6GR AI/ML 研究中的三个共性问题：

1. **如何判断 AI/ML 是否真正带来收益**：建立统一但可按用例细化的评估指标体系。
2. **如何管理 AI/ML 模型及其功能**：讨论模型部署、切换、监测、训练和更新所需的生命周期管理（LCM）框架。
3. **如何获得训练、验证和评估所需的数据**：明确数据收集的内容、格式、范围以及 RAN1 与其他工作组之间的职责边界。

本章的基本逻辑可以概括为：

> 先定义收益和代价如何衡量，再定义模型如何被管理，最后定义支撑这些过程所需的数据如何产生和传递。

## 3.1 评估与 KPI

### 3.1.1 为什么需要新的评估体系

原文指出，传统 5G NR 研究中已经使用了中间指标和系统指标，但 AI/ML 用例还会引入一组新的影响因素，例如：

- 模型计算复杂度；
- 推理时延；
- 训练或微调时延；
- 模型存储需求；
- AI/ML 处理带来的功耗；
- UE 与网络之间的厂商间协作复杂度；
- 不同场景、不同小区和不同部署条件下的泛化能力。

如果只比较 BLER、吞吐量或 NMSE，可能会高估 AI/ML 的实际价值。例如，一个模型可能在链路级仿真中提高了预测精度，但同时带来了大量 CSI 反馈、模型更新、性能监测或在线微调开销。此时，单看模型精度无法证明系统收益成立。

因此，本节试图把 AI/ML 的收益和成本放到同一个评估框架中。

### 3.1.2 Proposal 3.1：初始评估指标框架

Proposal 3.1 将评估指标分为四类。

#### A. 性能相关指标

性能指标需要覆盖三个层次：

1. **模型层中间指标**：衡量 AI/ML 模型自身的预测或重构质量，例如预测误差、重构误差、相似度等。
2. **链路层指标**：衡量模型对无线链路的直接影响，例如 BLER、误码表现、解调性能等。
3. **系统层指标**：衡量最终系统效果，例如吞吐量、资源开销、用户体验或服务能力。

原文特别强调，开销不能只统计传统空口资源开销，还应考虑 AI/ML 运行链路中的附加开销，包括：

- 模型推理产生的计算和处理开销；
- 性能监测所需的参考数据、反馈和测量开销；
- 模型重新训练或更新的开销；
- 后续提出的在线微调和特定场景微调开销。

#### B. AI/ML 模型相关指标

模型相关指标主要用于衡量“模型是否值得部署”，包括：

- 模型复杂度和计算复杂度；
- 推理时延；
- 训练时延，尤其是需要在线训练时；
- 功耗；
- 后续补充的模型存储需求；
- 可扩展性，尤其是双侧模型和多厂商协作场景下的可扩展性。

原始 Proposal 3.1 对功耗只保留了待进一步研究的表述，说明当时尚未确定统一的功耗测量方法。

#### C. 厂商间协作

对于双侧模型、可下载模型、可上传模型或 UE 与网络共同完成推理的场景，训练、验证、模型交付和模型更新可能涉及不同厂商。因此需要评估：

- 厂商间协作本身的复杂度；
- 协作对性能的影响；
- 数据、模型、标签和测试条件是否能够跨厂商复现；
- 模型是否依赖特定设备、特定网络或特定厂商实现。

这意味着 AI/ML 用例的评价对象不只是单一模型，而是一个包含 UE、网络、数据、模型管理和协作流程的系统。

#### D. 泛化性能

原文要求研究模型在较大范围条件下的泛化能力，并进一步讨论如何定义真实部署场景。

可能涉及的条件包括：

- 不同小区；
- 不同用户移动轨迹；
- 不同信道和传播环境；
- 不同设备能力；
- 不同负载和调度状态；
- 不同训练数据与实际推理数据的分布差异。

这里的关键问题是：一个模型在单一仿真场景中有效，并不等于它在真实网络中有效。泛化性能因此被视为 AI/ML 是否具备规范化价值的重要依据。

### 3.1.3 各公司对 Proposal 3.1 的主要意见

#### 1. 应把在线微调开销纳入系统评价

Futurewei 和 IIT Kanpur 支持将在线微调纳入开销统计。其理由是，在线微调并不是免费的：模型需要采集新数据、执行更新、进行验证，并可能在更新期间产生额外信令和计算负担。

这会改变吞吐量或性能收益的计算方式。更合理的比较应当是：

```text
实际系统收益
= AI/ML 带来的性能收益
- 推理开销
- 监测开销
- 训练/微调开销
- 信令与反馈开销
```

#### 2. 需要考虑模型存储和模型规模

Lenovo 提议将模型存储需求明确加入模型相关指标。对于 UE 侧模型，存储空间可能影响：

- UE 是否具备部署条件；
- 可同时保存和激活的模型数量；
- 模型切换速度；
- 固件、内存和 AI 加速器的设计；
- 多个 AI/ML 功能并发运行时的资源竞争。

因此，模型规模不应只被理解为文件大小，还应与运行时内存、缓存、模型加载和多模型共存联系起来。

#### 3. 最终系统指标与中间指标如何平衡

Ericsson 建议结论应主要基于最终性能指标，例如吞吐量，而不是只基于中间指标。其逻辑是：模型精度提升只有转化为系统级收益，才具有实际价值。

Qualcomm 对这一表述进行了进一步修正，认为不应使用“最终指标替代中间指标”的绝对说法，而应改为：

> 最终性能指标应与中间 KPI 一起使用。

原因包括：

- 某些用例没有唯一、明确的最终系统指标；
- 中间指标能够解释性能变化的原因；
- 系统级指标可能受调度、负载和实现细节影响，难以单独归因于 AI/ML；
- 在研究早期，完整系统级评估可能尚未具备条件。

因此，更稳妥的评价方式是“分层报告、联合判定”：既报告模型层和链路层指标，也尽量报告系统层结果。

#### 4. 功耗不能简单等同于模型复杂度

Xiaomi 指出，功耗不只取决于模型参数量或计算量，还与以下因素相关：

- 推理频率；
- 模型是否持续驻留在 AI 引擎中；
- 空闲状态下的基础功耗；
- 数据采集、预处理和后处理；
- 模型下载、切换和更新；
- UE 与网络两侧的功耗分布。

因此，仅以 FLOPs 或模型复杂度估算能耗可能不够准确。更完整的功耗评价应当考虑“每次推理功耗”和“完整服务周期功耗”。

#### 5. 训练时延是否应作为统一 KPI

CATT/CICTCI、Xiaomi 和 OPPO 对训练时延的普遍意见是：

- 训练时延高度依赖硬件和实现；
- 大多数用例使用离线训练，并不要求实时训练；
- 只有在线训练或快速微调场景才真正关心训练时延；
- 如果所有用例都强制评估训练时延，结果可能缺乏可比性。

这说明训练时延更适合作为**条件性指标**，而不是所有 AI/ML 用例必须统一报告的硬性指标。

#### 6. 泛化场景需要具体化

SPRD、SK Telecom 和 CMCC 认为“广泛条件下的泛化性能”过于模糊。CMCC 特别指出，如果模型支持重训练或微调，那么 UE 移动到不同区域后可以更新模型，此时不一定需要要求一个模型覆盖所有场景。

因此，泛化评估需要进一步明确：

- 是跨小区泛化，还是跨区域泛化；
- 是跨用户泛化，还是跨设备泛化；
- 是不允许更新模型的静态泛化，还是允许在线微调的动态适应；
- 是否需要覆盖非理想硬件和真实部署条件。

#### 7. Token 通信等新业务需要新的系统指标

Huawei/HiSilicon 建议增加面向 AI/ML 服务的指标，例如 Token 通信的服务效率。这表明 AI/ML 不仅是无线链路中的一个算法，也可能改变业务流量形态和服务目标。

未来可能需要针对 Token 流量定义：

- Token 单元的传输效率；
- Token 错误率或错误识别率；
- Token 级时延；
- 面向生成式业务的有效吞吐量；
- 调度和 HARQ 对 Token 流量的适配能力。

### 3.1.4 Proposal 3.1（new）：修订后的方向

在前述意见基础上，Proposal 3.1（new）形成了更完整的版本，主要新增或强化了以下内容：

1. **明确纳入在线微调开销**：包括推理、性能监测和在线微调。
2. **强调结论应参考最终系统指标**：例如吞吐量，而不是只看中间模型指标。
3. **加入可扩展性**：尤其适用于双侧模型、多用户和多设备场景。
4. **明确厂商间协作复杂度及其性能影响**。
5. **保留广泛条件下的泛化性能**，同时继续讨论真实部署场景如何定义。
6. **加入 RAN4 互操作性测试的可行性和复杂度**。

### 3.1.5 Proposal 3.1（new）的争议

修订后的版本仍然存在三类分歧：

#### A. 最终指标是否优先于中间指标

部分公司支持以吞吐量等最终指标作为主要结论依据，另一部分公司认为中间指标不能被排除。较合理的理解是：

- 中间指标用于解释模型是否有效；
- 链路级指标用于解释无线传输是否改善；
- 系统级指标用于判断整体收益；
- 结论应根据用例实际可获得的指标综合作出。

#### B. 公共框架是否会增加重复工作

CMCC 认为，如果每个用例已经分别定义了评估指标，额外增加一个通用提案可能没有必要。这反映出一个现实问题：通用框架可以提高一致性，但也可能与各用例的局部评估重复。

#### C. 不是所有用例都有唯一的“最终性能指标”

对于模型压缩、模型管理、数据收集或定位辅助等用例，最终收益可能由多个指标共同决定，不能简单归结为吞吐量。因此，最终指标的定义需要按用例制定。

## 3.2 生命周期管理（LCM）框架

### 3.2.1 LCM 的含义

LCM（Life Cycle Management，生命周期管理）不是单纯的模型下载流程，而是覆盖 AI/ML 功能从准备到退役的完整管理过程，包括：

- 模型或功能的标识；
- 模型和数据的管理；
- 模型传输与交付；
- 模型配置、激活、停用和切换；
- 推理过程的性能监测；
- 模型训练、重新训练和微调；
- 模型在不同场景或不同小区中的适用性；
- 模型失效后的回退处理；
- 模型、功能与硬件处理资源之间的协调。

### 3.2.2 为什么以 5G NR LCM 为起点

本节的基础提案是：6G 空口 AI/ML 的 LCM 可以把 5G NR Rel-19 中已经采用的 AI/ML LCM 机制作为起点，例如 TS 38.331 中的相关框架。

这样做的目的不是直接复制 5G 机制，而是：

- 利用已有规范和流程基础；
- 避免 6G 重新设计一套完全孤立的模型管理方式；
- 继承已有的配置、能力上报和模型管理经验；
- 在 5G 基础上识别 6G 的新增需求。

### 3.2.3 Proposal 3.2 的初始研究范围

原始 Proposal 3.2 主要提出研究以下增强方向：

#### A. 数据与模型管理

需要研究模型、训练数据、标签、模型版本和模型适用条件之间如何关联。数据与模型管理还涉及模型验证、模型更新和模型是否适合当前设备/网络条件。

#### B. 附加条件处理

模型可能只在特定信道、特定小区、特定设备能力或特定配置下有效。因此 LCM 需要支持识别和处理这些附加条件。

#### C. 连续在线训练或微调

对于环境变化明显的场景，模型可能需要在线训练、现场特定微调或持续适应。这里的关键是如何在不破坏通信可靠性的情况下完成更新。

#### D. AI/ML 处理与存储框架

需要考虑 AI/ML 计算单元、内存、模型驻留、并发模型和资源分配。Samsung 还提出了 AI/ML memory unit（MU）的设想，用于管理同时激活的 AI/ML 功能和模型。

#### E. 统一 LCM

原文注释提出，应努力形成跨用例的统一 LCM，而不是为 CSI、DMRS、波束管理、定位等每个用例设计完全不同的模型管理流程。

### 3.2.4 各公司对 LCM 框架的主要意见

#### 1. 统一框架与用例差异之间的矛盾

一部分公司支持统一 LCM，理由是：

- 可以减少重复信令和重复设计；
- 可以统一模型标识、配置、更新和监测流程；
- 有利于多种 AI/ML 功能共存；
- 可以利用不同用例之间的共同数据和模型结构。

另一部分公司担心不同用例差异太大。例如：

- AI 接收机与 CSI 反馈的输入输出不同；
- DMRS 开销降低与波束预测的时延要求不同；
- UE 侧模型与网络侧模型的资源约束不同；
- 有些模型需要在线适配，有些模型只需离线训练。

因此，“统一”更适合体现在共性管理流程上，而不应强迫所有用例使用相同的模型结构、相同的训练时序或相同的性能要求。

#### 2. RAN1 与 RAN2 的职责边界

Huawei/HiSilicon、Xiaomi 等公司指出，LCM 框架与协议流程很大程度上属于 RAN2 的工作范围，RAN1 不宜单独决定完整的 6G LCM 架构。

这里需要区分两件事：

- **RAN1 可以研究的内容**：物理层用例对模型配置、切换、数据、能力、训练和性能反馈提出的需求。
- **RAN2 更适合决定的内容**：具体 RRC 信令、协议状态机、配置流程和跨层管理架构。

因此，RAN1 的合理定位是输出 AI/ML 用例的需求和约束，而不是直接规定全部 LCM 协议。

#### 3. “on-device”是否过窄

Futurewei 建议删除“on-device”，因为在线训练或微调也可能发生在网络侧。vivo、Qualcomm 等公司则认为，如果当前重点是 UE 侧 AI/ML 能力和 UE 侧训练，那么保留 on-device 有其必要性。

这实际上涉及两个概念：

- **在线训练/微调**：强调时间特性，指模型在运行期间更新；
- **设备侧训练/微调**：强调位置特性，指训练发生在 UE 上。

两者不是同义词。在线训练可以发生在 UE，也可以发生在网络；设备侧训练则一定发生在 UE。因此更准确的规范表述应明确区分训练的**时序**和**位置**。

#### 4. 性能监测应成为 LCM 的组成部分

Fujitsu、Ofinno、InterDigital 等公司认为，模型部署后必须监测其实际性能，否则无法判断模型是否仍然适用。

性能监测可能用于：

- 生成模型性能参考值；
- 判断模型是否发生性能退化；
- 触发模型切换或回退；
- 决定是否需要重新训练或微调；
- 评估模型在新小区、新设备或新信道中的适用性。

这也是为什么第 3.1 节将性能监测开销纳入 KPI，而第 3.2 节又将性能监测纳入 LCM。

#### 5. 跨小区连续性与模型切换

CATT/CICTCI 提出，需要研究 UE 侧 AI/ML 功能跨小区连续运行的问题，特别是在切换附近避免模型突然失效。

LG Electronics 进一步提出：

- 更快、更高效的模型或功能切换；
- AI 模型失效时回退到非 AI 方案；
- 对尚未激活的模型进行性能监测；
- 在多个候选模型之间进行可靠选择。

这说明 LCM 不应只关注“如何下载模型”，还需要关注模型在真实网络移动过程中的连续服务能力。

#### 6. Rel-19 是否足够作为起点

CMCC 指出，如果考虑双侧模型，仅参考 Rel-19 可能不够，还需要结合 Rel-20 以及 TS 38.331、TS 38.214、TS 38.212 等多个规范。

NEC 和 OPPO 则认为，现有 5G NR AI/ML LCM 可能较偏向 CSI 用例，对 DMRS 开销降低等非 CSI 用例并不完全适用。

因此，本节的合理结论不是“直接复用 5G LCM”，而是：

> 以 5G NR 的已有 LCM 机制为参考基线，系统评估哪些机制可以复用，哪些机制需要扩展或重新抽象。

### 3.2.5 Proposal 3.2：修订后的 LCM 方向

修订后的 Proposal 3.2 增加或明确了以下内容：

- 数据和模型管理，并注明其主要由 RAN2 负责；
- 性能监测；
- 附加条件处理，例如 UE 侧 AI/ML 功能跨小区连续性；
- 连续在线或特定场景的设备侧训练/微调；
- AI/ML 处理和内存框架；
- 利用跨用例相似性实现统一 LCM；
- 保留“跨用例统一 LCM”的研究目标。

### 3.2.6 LCM 章节的核心技术含义

本节实际上提出了一个分层的 LCM 思路：

#### 共性层

适用于多种用例的公共能力，包括：

- 模型标识；
- 模型版本和能力管理；
- 模型传输；
- 激活、停用和切换；
- 性能监测；
- 失效回退；
- 基本的数据和模型管理。

#### 用例层

根据 CSI、DMRS、波束管理、定位等用例分别定义：

- 输入输出格式；
- 训练和标签方式；
- 适用条件；
- KPI；
- 时延与可靠性要求；
- 是否需要 UE 与网络协作。

这种分层方式可以同时保留统一框架的可复用性和不同用例的灵活性。

## 3.3 数据收集框架

### 3.3.1 数据收集为什么成为独立问题

AI/ML 方案的性能高度依赖数据。对于无线空口 AI/ML，数据不仅包括普通业务数据，还可能包括：

- CSI-RS、DMRS、SRS 等参考信号观测；
- 接收信号、信道估计和噪声信息；
- 位置、波束、移动性和环境信息；
- 模型输入、模型输出和标签；
- 训练、验证和测试数据的划分信息；
- 模型性能监测所需的真实参考值；
- 不同 UE、网络和小区之间的关联信息。

因此，数据收集方式会直接影响模型训练、泛化评估、在线更新和跨厂商互操作。

### 3.3.2 本节总结的三个讨论问题

#### A. 面向未来且跨工作组统一的数据收集框架

第一项讨论是：是否应增强现有数据收集框架，使其能够服务未来的多种 AI/ML 用例，并且跨 RAN1、RAN2、RAN4 等工作组保持一致。

重点不只是“收集更多数据”，而是建立统一的数据描述、数据格式和数据传递方法。

#### B. 数据收集的范围和限制

第二项讨论是：数据收集到底应该是用例专用，还是支持更通用的用途。

两种方向各有优缺点：

| 方向 | 优点 | 风险 |
| --- | --- | --- |
| 用例专用数据收集 | 开销较小，需求明确，容易与具体 KPI 对齐 | 难以复用，后续新增用例可能需要重新设计 |
| 通用数据收集 | 便于复用，支持多模型和后续研究 | 数据量、信令、存储和隐私开销可能较大 |

#### C. 是否引入新的 AI/ML 数据管理平面

第三项讨论是是否需要设计一个新的 AI/ML 数据管理平面。这个问题涉及：

- 数据采集任务如何配置；
- 数据如何从 UE 上传到网络；
- 数据如何与具体模型、版本和用例关联；
- 数据的权限、隐私和生命周期如何管理；
- 数据收集是否需要独立于现有控制面和用户面。

原文同时承认，其中一些内容可能超出 RAN1 的直接职责。因此 RAN1 更适合先识别物理层 AI/ML 用例所需要的数据内容和数据格式，再由相关工作组决定具体协议和管理机制。

### 3.3.3 Conclusion 3.3（RAN1 第 122bis 次会议版本）

初始结论是：

> 对于 6GR AI/ML 研究，RAN1 研究每个用例的数据收集内容和格式。

这个结论有三个特点：

1. **按用例展开**：不同用例分别确定需要什么数据。
2. **聚焦内容与格式**：RAN1 主要描述数据需求，而不是直接定义完整的数据管理协议。
3. **保持工作组分工**：具体收集流程和协议可交由相关工作组继续处理。

### 3.3.4 各公司对数据收集结论的主要意见

#### 1. 需要明确训练数据

Lenovo 建议明确说明，数据收集至少应包括模型训练数据，尤其是离线训练数据。

这很重要，因为“数据收集”可能被理解为只收集在线推理或运行时测量数据，而离线训练数据同样是 AI/ML 方案成立的基础。

#### 2. UE 侧和网络侧都应考虑

Lenovo 多次要求澄清 UE 侧和网络侧数据收集是否都在范围内。对于不同模型位置，数据来源不同：

- UE 侧模型可能需要 UE 本地测量、信号样本和设备状态；
- 网络侧模型可能需要来自多个 UE 的聚合数据；
- 双侧模型还需要保证编码器和解码器两侧数据的一致性；
- 在线微调可能需要实时采集当前环境数据。

因此，结论中应明确数据收集的实体位置，而不能只说“收集数据”。

#### 3. 离线训练、在线训练和微调是否都包括

Fujitsu 询问该结论是否同时适用于：

- 离线训练；
- 在线训练；
- 在线微调或特定场景微调。

CMCC 也建议在每个用例中分别讨论离线训练和在线训练。不同训练方式对时延、数据新鲜度、信令和隐私有不同要求，因此不能假定同一套数据收集机制适用于全部情况。

#### 4. RAN1 是否应研究数据管理框架

Nokia 认为数据收集框架更适合由 RAN2 讨论。SK Telecom 也支持研究数据需求，但对这是否属于 RAN1 范围保持谨慎。

CATT/CICTCI 则提出了一个更具体的问题：例如 CSI 相关 AI/ML 数据收集是否应嵌入 CSI 报告流程，RAN1 是否需要分析这种物理层集成方式的优缺点。

这体现了数据收集问题的两层结构：

- **需求层**：AI/ML 用例需要哪些字段、标签、采样和格式；
- **协议层**：这些数据通过哪个信令、哪个报告过程和哪个工作组机制传输。

本章倾向于让 RAN1 负责前者，并向后者提供需求输入。

### 3.3.5 Conclusion 3.3（new）：修订后的结论

修订后的结论增加了一个限制条件：

> RAN1 至少研究每个用例中与离线训练相关的数据收集内容和格式。

相比旧版本，主要变化是加入了“至少包括离线训练”。其效果是：

- 确保最基本的训练数据需求不会被遗漏；
- 避免在尚未明确在线训练机制之前扩大研究范围；
- 给 RAN1 一个更清晰、可落地的最低研究边界；
- 为后续按用例扩展在线训练和微调留下空间。

不过，Google 进一步提醒还应考虑 UE 复杂度，例如 CPU 负担。也就是说，数据收集本身会消耗 UE 计算、存储、能量和通信资源，不能只从网络侧观察数据是否可获得。

### 3.3.6 数据收集章节的核心技术含义

数据收集不是 AI/ML 系统之外的辅助工作，而是模型生命周期的一部分。它至少需要与以下对象建立关联：

```text
数据样本
  -> 数据类型与格式
  -> 用例和模型版本
  -> 标签或监督信号
  -> 训练/验证/测试用途
  -> 数据来源（UE、网络或双侧）
  -> 采集时机（离线、在线、微调）
  -> 资源成本与隐私约束
```

如果这些关系没有定义清楚，就会出现以下问题：

- 不同厂商使用不同数据定义，结果无法比较；
- 训练数据和测试数据分布不一致，泛化结论失真；
- UE 侧和网络侧的输入无法对齐，双侧模型难以协作；
- 在线微调缺少标签或参考值，无法判断更新是否有效；
- 数据采集开销被遗漏，导致 AI/ML 收益被高估。

## 4. 第三章的整体逻辑

### 4.1 从“算法性能”转向“系统可部署性”

第三章最重要的变化，是不再把 AI/ML 只当作一个提高预测精度的算法，而是将其看作一个需要长期运行的系统能力。

因此，评估对象从单一模型扩展为：

```text
模型性能
+ 空口性能
+ 系统吞吐量和服务能力
+ 推理、监测、训练和反馈开销
+ 功耗、存储和处理能力
+ 跨厂商协作
+ 泛化与模型切换
+ 数据收集与生命周期管理
```

### 4.2 三个最核心的权衡

#### 权衡一：最终性能指标 vs. 中间模型指标

- 中间指标能解释模型是否学得好；
- 链路指标能解释无线传输是否改善；
- 系统指标能解释用户是否真正受益；
- 三者不能简单互相替代。

更合理的做法是按层次报告，并根据具体用例确定最终判定指标。

#### 权衡二：统一 LCM vs. 用例差异

- 统一 LCM 有利于复用和跨用例协作；
- 但 CSI、DMRS、波束管理和定位的模型位置、时延和数据要求差异很大；
- 因此应统一管理流程和公共能力，而不是强行统一所有用例的具体行为。

#### 权衡三：研究范围 vs. 工作组职责

- RAN1 需要识别物理层用例需求；
- RAN2 更适合定义协议、RRC 和数据管理流程；
- RAN4 需要关注互操作性和测试；
- AI/ML LCM 和数据收集必须通过跨工作组协作完成。

## 5. 对 AI/ML 研究和系统设计的启示

以下内容是基于第三章的工程性归纳，不是原文新增协议结论。

### 5.1 评估时应建立“收益-成本”闭环

任何 AI/ML 用例都不应只提供模型精度。至少应同时给出：

- 模型层效果；
- 链路层效果；
- 系统层效果；
- 推理和监测开销；
- 训练或微调开销；
- 模型存储与计算资源；
- 泛化条件和失败场景。

### 5.2 训练数据必须从一开始纳入方案设计

需要在实验设计中提前明确：

- 模型输入和输出；
- 标签如何获得；
- 标签是理想值、估计值还是自监督信号；
- 数据由 UE、网络还是双方产生；
- 训练、验证和测试如何划分；
- 数据采集是否引入额外空口或计算开销。

### 5.3 模型管理应支持失败回退

由于模型可能存在场景失配、性能退化或切换延迟，工程系统应考虑：

- 非 AI 基线回退；
- 旧模型回退；
- 模型版本并存；
- 激活模型和候选模型的性能监测；
- 小区切换时的模型连续性；
- 模型更新前后的安全验证。

### 5.4 离线训练不等于不需要运行时机制

即使模型采用离线训练，运行时仍然需要：

- 模型适用性判断；
- 性能监测；
- 场景失配检测；
- 模型切换或回退；
- 必要时的数据采集和再训练触发。

因此，离线训练只改变训练时机，不会消除 LCM 和数据管理需求。

## 6. 小结

第三章为 6GR AI/ML 研究建立了三个基础支柱：

1. **评估体系**：从模型精度扩展到链路、系统、复杂度、功耗、存储、泛化和厂商间协作。
2. **LCM 框架**：以 5G NR AI/ML LCM 为参考起点，但需要面向 6G 的多用例、双侧模型、跨小区连续性、性能监测和在线/特定场景微调进行增强。
3. **数据收集框架**：至少明确每个用例离线训练所需的数据内容和格式，并逐步扩展到在线训练、微调、UE/网络侧数据收集和跨工作组协作。

本章真正推动的不是某一个具体 AI/ML 算法，而是把 AI/ML 从“可行的算法实验”推进到“可评估、可管理、可部署、可互操作的无线系统功能”。
