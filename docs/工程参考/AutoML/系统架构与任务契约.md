## 12. 生产级 Agentic AutoML 系统设计蓝图

<a id="s12-1"></a>

### 12.1 设计目标与非目标

**目标**：针对表格分类/回归任务，让用户输入目标、数据引用和资源约束，系统自动完成数据审计、验证设计、强 baseline、受控搜索、候选比较、必要的开放式改进和可追溯交付。

**非目标**（第一阶段）**：允许任意生产数据库写入、自动发布到线上而不经审批、在最终测试集上无限制调参、无资源上限的代码执行、无审计的自主互联网检索、绕过许可证的第三方模型使用。**

<a id="s12-2"></a>

### 12.2 九层架构

| 层 | 建议组件 | 输入 | 输出 | 强约束 |
|---|---|---|---|---|
| 1. Task Intake | schema 校验、自然语言规范化 | 用户目标、数据 ID、限制 | `TaskSpec` | 禁止隐式更改核心目标 |
| 2. Data Profile | 列类型、缺失、重复、目标检查 | 只读数据快照 | `DataProfile` | 默认不读取原始敏感值进入 LLM |
| 3. Evaluation Design | split policy / metrics / leakage checker | 业务规则、数据画像 | `EvalContract` | 测试标签隔离 |
| 4. Baseline Service | AutoGluon/FLAML/简单模型 | 训练数据、预算 | baseline artifacts | 必须首个有意义的参照 |
| 5. Plan & Retrieval | planner、经验库、RAG | task/profile/baseline | 候选假设列表 | 候选数和范围有限 |
| 6. Search Service | Optuna/SMAC/Ray | typed trial configs | trial metrics | GPU、内存、并发限额 |
| 7. Execution Sandbox | 容器/低权进程 | 许可代码、dataset mount | logs、artifacts | 网络、系统调用、路径限制 |
| 8. Evaluation & Audit | CV evaluator / policy validator | 不可变预测、日志 | 可信 scorecard | Agent 不能自行改评测器 |
| 9. Delivery & Monitoring | registry / approvals / drift | final bundle | model card/deploy | 人类审批和回滚 |

<a id="s12-3"></a>

### 12.3 TaskSpec：所有 agent 共享的唯一任务契约

任务契约应在正式训练前固定，并用显式变更记录维护：

```yaml
schema_version: 1
request_id: demo-001
objective:
  task_type: binary_classification
  target: churned
  primary_metric: roc_auc
  maximize: true
data:
  dataset_id: warehouse://snapshot/churn_2026_10_01
  entity_key: customer_id
  observation_time: event_time
  label_available_time: label_time
  forbidden_features:
    - post_churn_refund
validation:
  strategy: temporal
  train_end: '2026-06-30'
  validation_start: '2026-07-01'
  validation_end: '2026-08-31'
  test_start: '2026-09-01'
  test_end: '2026-09-30'
  group_key: customer_id
budget:
  max_wallclock_seconds: 7200
  max_gpu_hours: 4
  max_llm_usd: 15
  max_experiments: 40
constraints:
  max_p99_inference_ms: 100
  max_model_size_mb: 300
  human_approval_before_deploy: true
security:
  container_network: disabled
  production_write_access: false
  pii_in_prompt: false
```

**上述日期、资源、金额均为架构示例，不是论文推荐统一值。**真实合同应根据数据时效和任务风险修改。尤其当标签出现时间晚于特征时间时，应构造 point-in-time 正确的特征提取，避免看见未来信息。

<a id="s12-4"></a>

### 12.4 Data Profiler：哪些信息值得送给 Agent

推荐结构化摘要：

- 数据行数、列数、目标缺失率、标签分布；
- 主要数据类型、类别基数、主键候选、重复键比例；
- 数值/类别特征缺失、异常值、常量列；
- 时间列、潜在 entity ID、分组相关性；
- 列名、数据字典语义、统计聚合；
- 被许可的样本数据（脱敏且必要时）；
- 潜在泄漏信号（与标签时间关系、几乎完美相关、明显后验字段）；
- 数据限制和可用计算资源。

**不建议**把全量训练数据转为文本塞入 LLM 上下文。既不高效，也可能造成隐私、成本和精度问题。Agent 看概要，训练器读实际数据。

<a id="s12-5"></a>

### 12.5 验证方案绝对优先于建模选择

正确的验证方案对最终系统效果影响可能大于更换模型。推荐优先级：

1. **Time series / 时序决策**：时间切分、训练窗口与 embargo、避免未来值泄漏；
2. **多样本同实体**：GroupKFold 或 group holdout，避免同一客户/患者跨训练验证混合；
3. **普通 IID 分类**：合适时使用 Stratified K-fold 或分层 holdout；
4. **极小样本**：考虑重复 CV / 嵌套 CV，但成本高；
5. **在线 A/B**：需要额外业务实验、不能拿离线数据分数代替线上因果效果。

不推荐让 Agent 通过尝试多种切分方式挑一个“分数最高”的方式。切分策略应基于真实部署时的可用信息制定，并在比较模型前固定。

<a id="s12-6"></a>

### 12.6 搜索计划编排：先易后难

一个受控计划可以分为四层：

- **P0 最小可信 baseline**：Dummy/linear/树模型，验证数据管线与指标能计算；
- **P1 成熟 AutoML**：AutoGluon 或 FLAML，在固定预算内获得稳健组合；
- **P2 结构化优化**：针对候选模型族使用 Optuna/SMAC 调整重要参数、阈值、代价；
- **P3 自由探索**：仅在有明确收益空间时，允许 agent 提出特征改造、损失设计或代码补丁。

P3 若不能在限定次数内复现明显收益，应该回退 P1/P2；不能因为开放式 agent“觉得更先进”，就舍弃可复现的强基线。

<a id="s12-7"></a>

### 12.7 实验队列与资源服务

**任务状态**：`queued → allocated → running → completed/failed/cancelled → verified`。每个 trial 记录：

- `experiment_id`、`parent_id`、`hypothesis_id`、`run_id`；
- `code_hash`、`dataset_hash`、`container_digest`、`seed`；
- `resource_request`、`resource_actual`、`start/end_time`；
- `train_metrics`、`validation_metrics`、`predict_latency`；
- `error_type`、`error_trace`（必要时脱敏）；
- `artifact_locations`、`evaluation_contract_version`。

**调度原则**：同一数据切分/目标/硬件预算下维护 best-so-far，超出预算时不接受新试验。对 OOM 可有限次数自动降 batch size，但必须标记配置发生改变。

<a id="s12-8"></a>

### 12.8 日志、可观测性与审计

至少记录四种事件：

```text
agent_decision: 为什么选择这个候选，以及引用了什么经验
trial_submitted: 配置、资源、数据/评估契约 hash
trial_finished: 真实运行指标、错误、成本、产物
policy_gate: 是否违反泄漏/资源/权限/上线规则
```

对每个 LLM 调用记录模型 ID、prompt 版本、上下文来源的文档 ID、token 使用量、响应 schema 和调用失败情况。安全敏感日志可存加密标识符，避免直接暴露原始训练数据、凭据或完整隐私样本。

<a id="s12-9"></a>

### 12.9 何时需要 human-in-the-loop

必须或强烈建议人工审核的节点：

- 标签、预测时点、业务损失函数有歧义；
- 处理受监管或敏感领域数据；
- 改变训练/验证切分契约、数据范围、推理策略；
- 需要联网安装未审核依赖；
- Agent 提出可能改变标签分布的重采样或数据删除；
- 需要写回业务系统、启动线上 A/B、自动部署；
- 模型性能与公平性/风险指标冲突。

这些不是 agent 能力弱的“临时补丁”，而是可信 ML 系统的责任分配原则。

<a id="s12-10"></a>

### 12.10 MLOps 集成边界

建议把自动化训练与生产推理分离：

- **Feature Store**：固定训练/推理特征语义；
- **Experiment Tracker**：记录模型/配置与评测；
- **Model Registry**：只接收已验证的版本；
- **CI 验证**：测试输入 schema、依赖、离线重跑与回滚；
- **Serving**：根据延迟、吞吐与成本限额选择部署；
- **Monitoring**：输入/标签漂移、特征缺失、预测分布、线上性能、错误与反馈闭环。

Agent 可以提出操作，但上线审批和数据权限应由独立的规则引擎执行，不能由 Agent 自行授予自己更高权限。
