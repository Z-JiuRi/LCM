## 5. 候选决策与执行流程

<a id="s5-1"></a>

### 5.1 端网协商流程（双侧配对特例）

```text
[gNB Agent]                        [UE Runtime]

    │
    ├─ 1. 检测退化/触发条件
    │    (KPI 下降、环境变化、周期检查)
    │
    ├─ 2. 查询候选配对
    │    model_repository_query()
    │    → 候选: [(enc1, dec1), (enc2, dec2), ...]
    │
    ├─ 3. 请求 UE 能力与状态 ────────────►
    │                                      ├─ local_resource_check()
    │                                      ├─ 返回: 内存、电量、当前模型
    │    ◄────────────────────────────────┤
    │
    ├─ 4. 提议配对方案 ──────────────────►
    │    PREPARE(pair_manifest, enc_url)  │
    │                                      ├─ 5. 本地验证
    │                                      ├─   • 下载 encoder (如需)
    │                                      ├─   • compatibility_verify()
    │                                      ├─   • shadow_test()
    │                                      ├─   • proxy_decoder_eval()
    │                                      │
    │    ◄────────────────────────────────┼─ 6. READY(evidence) 或 REJECT
    │
    ├─ 7. 决策：COMMIT / HOLD / RETRY / ESCALATE
    │    (基于 evidence 新鲜度、资源、风险)
    │
    ├─ 8. (若 COMMIT) 预留资源
    │    resource_reservation.lock()
    │
    ├─ 9. COMMIT(transaction_id, epoch) ─►
    │                                      ├─ 10. 最终检查
    │                                      ├─   • resource_check() 再次确认
    │                                      ├─   • 持久化 epoch 到本地状态
    │                                      │
    │    ◄────────────────────────────────┼─ 11. ACK 或 ABORT
    │
    ├─ 12. (收到 ACK) 更新 gNB decoder
    │     持久化配对状态
    │
    └─ 13. 数据面：检查 epoch 一致性
         UE: if (received_epoch != local_epoch) → reject/fallback
```

**故障恢复点**：
- PREPARE 超时 → 重试或选择其他候选
- READY 未到达 → HOLD，等待或降级
- ACK 丢失 → UE 凭持久状态识别已完成；gNB 幂等重传
- 崩溃恢复 → 读取持久日志，确认 epoch 或回退

### 5.2 单侧功能更新流程（波束管理示例）

```text
[gNB Agent]                        [UE Runtime]

    │
    ├─ 1. UE 定期上报性能摘要（可选）
    │    • top-k 准确率下降
    │    • 输入分布统计
    │
    ├─ 2. gNB 监测网络侧信号
    │    • 波束失败率
    │    • 切换频率
    │
    ├─ 3. 决策：需要补测、校准还是换模型？
    │    (LLM 规划 或 规则/统计方法)
    │
    ├─ 4a. 若补测：扩展 top-K 或 full scan ─►
    │                                      ├─ 执行测量
    │    ◄────────────────────────────────┼─ 返回测量结果
    │
    ├─ 4b. 若校准：请求传感器/锚点校准 ───►
    │                                      ├─ 重新校准定位或天线
    │    ◄────────────────────────────────┼─ 确认
    │
    ├─ 4c. 若换模型：下发新模型 ──────────►
    │    包含 manifest + 模型文件           │
    │                                      ├─ 本地验证 → shadow test
    │    ◄────────────────────────────────┼─ READY 或 REJECT
    │
    ├─ 5. COMMIT / HOLD
    │
    └─ 6. 本地 fallback 能力
         UE 自主检测失效 → 切换到传统方法或旧模型
```

### 5.3 证据驱动决策流程

```text
输入：当前状态、候选动作集合、可用证据

[LLM Agent 或 决策器]
    │
    ├─ 1. 评估当前证据充分性
    │    • 证据是否过期？
    │    • 证据是否绑定正确的 config_epoch？
    │    • 不确定度是否可接受？
    │
    ├─ 2. 若证据不足，规划补测动作
    │    Decision: 补测什么？成本 vs 信息价值
    │    • 小规模 top-K 复核
    │    • 稀疏参考测量/标签
    │    • 请求 UE shadow test
    │
    ├─ 3. 执行补测（通过工具调用）
    │
    ├─ 4. 收集新证据后，重新评估
    │
    ├─ 5. 决策生命周期动作
    │    • 继续使用当前模型
    │    • 切换到候选模型 X
    │    • 触发有限微调（链路自适应场景）
    │    • 校准传感器/锚点（定位场景）
    │    • 等待更多证据
    │    • 拒绝并回退
    │
    ├─ 6. 提交执行（通过协调平面）
    │
    └─ 7. 监测执行结果，更新状态
```

**与基线比较**：
- 规则 LCM：固定阈值 + hysteresis
- 统计 LCM：变化检测 + 序贯检测
- 确定性工作流：DAG/状态机
- LCMAgent：考虑证据成本、时效、组合约束的动态规划
