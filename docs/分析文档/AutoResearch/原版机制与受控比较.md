### 21.5 拆开 Karpathy 原版 autoresearch：它如何实际工作？

<a id="s21-5-1"></a>

#### 21.5.1 三个关键文件与受控边界

**[AR01][AR02] 原始项目明确记录**：

| 文件 | 用途 | 原版 Agent 是否允许改 | 重要性 |
|---|---|---|---|
| `prepare.py` | 准备数据、tokenizer、数据加载、训练/评测基础常量、`evaluate_bpb` | **不允许** | 控制训练和度量契约；原版核心可信边界 |
| `train.py` | 小 GPT 模型、Muon + AdamW 等优化与训练逻辑 | **允许** | Agent 的主要可搜索代码空间 |
| `program.md` | Agent 的目标、运行规则、搜索策略、日志和回滚流程 | **由人设定与迭代** | 把研究方法程序化为自然语言“研究组织代码” |

原 README 指明单 NVIDIA GPU（项目在 H100 测试），Python 3.10+、`uv`，通过 `uv run prepare.py` 初始化、`uv run train.py` 试跑。每个**训练** run 固定约五分钟墙钟，不包含启动/编译开销。`val_bpb` 为验证 bits-per-byte 指标，数值越低代表在该验证协议下越好。README 特别提醒**不同硬件上的结果不可直接比较**。[AR01]

<a id="s21-5-2"></a>

#### 21.5.2 实验流程逐动作复现

```text
人工：设置目标、审定 program.md、确定环境和预算
   │
   ▼
建立分支 autoresearch/<tag> ──> 检查数据/基线
   │
   ▼
Agent 读取已有最优代码与此前实验记录
   │
   ▼
提出单个或少数代码变更 → 修改 train.py → git commit
   │
   ▼
启动训练：uv run train.py > run.log 2>&1
   │
   ├── 崩溃：读取 trace → 可修复则重试，不可修复则记录 crash
   │
   └── 成功：读取 val_bpb、VRAM、耗时
   │
   ▼
更新 results.tsv：commit、指标、显存、keep/discard/crash、变更说明
   │
   ├── 改善/值得保留 → 进入新基线
   │
   └── 未改善/不值得保留 → git reset 回滚
   │
   └───────────────────────────> 下一次实验
```

原始 `program.md` 明确使用独立分支、保存 `results.tsv`（不提交到 Git）、记录包含 Git 哈希的实验行；失败包括执行异常及超时，允许修复明显的小错误；对更复杂的实现要求提升足够明显，倾向保留在同等性能下更简单的代码。默认说明还要求开始后持续运行，直到人为中断；**这是一种原型研究默认规则，不是企业生产系统应该原样采用的运行策略**。[AR02]

<a id="s21-5-3"></a>

#### 21.5.3 为什么“五分钟”既聪明又有偏差

**聪明之处**：固定单次训练的时间预算，使一个候选模型的体积、速度和初期学习效果形成共同竞争；较小但训练快的架构可能比参数更多却只训练了很少 token 的架构得分更好。这激励“单位时间内有效模型进展”，不是只比较同等 step 数的最优 loss。

**潜在偏差**：

1. 它优化的是**该硬件 + 该数据 + 该时长**的短时表现；不必然对应 24 小时或 30 天的大规模训练表现。
2. 原项目排除了编译/启动开销，若工程部署时端到端吞吐重要，就必须另计总延迟和真实成本。
3. 单次短跑中有益的技巧，未必符合长程收敛稳定性、推理效率或质量评测。
4. 经过上百次自适应试验，单一验证集更容易被“研究过程”间接拟合。
5. 不同 GPU/驱动/编译版本可能改变可复现性；跨机器宣称直接 SOTA 需要统一硬件协议。

**应当如何解释成果**：在可复现的固定环境里，autoresearch 可以证明“发现了一个在五分钟代理目标上更好的训练方案”；若要宣称“产生通用新训练算法”，还需要多数据集、多模型尺寸、多预算、多个随机种子、独立测试和机制消融。

<a id="s21-7"></a>

### 21.7 一个关键实证：经典 HPO、纯 LLM 与 autoresearch 谁更强？

截至研究截止日，最直接的对比证据来自 Ferreira 等人的 **“Can LLMs Beat Classical Hyperparameter Optimization Algorithms? A Study on autoresearch”**（arXiv:2603.24647，初投 2026-03-25，2026-04-17 修订 v5）。该工作把 Karpathy 的小语言模型训练作为公共实验环境，而不是只凭概念推断哪种方法更强。[AR03][AR04]

<a id="s21-7-1"></a>

#### 21.7.1 论文的对比条件

- 固定**14 个超参数**的结构化 HPO 空间：TPE、CMA-ES、SMAC、Random、LLAMBO、LLM 直接提议 HP。
- 单独允许**直接修改代码**的 Karpathy Agent (Code)：它不局限于上述 14 个 HP；因此这组与固定空间方法的**候选集合并不严格相同**。
- 混合式 **Centaur**：CMA-ES 作为主优化器运行，约 30% 的 trial 接受 LLM 建议，并向 LLM 提供 CMA-ES 的均值向量、步长、协方差等状态；全部 trial 继续更新优化器。
- 实验主设置为单 H200 GPU、每次约五分钟训练、每组约 24 GPU 训练小时、3 个随机种子、显存上限约 76 GB。原作者明确说明 **LLM 推理开销未计入该 24 小时训练预算**，因此是**统一 GPU 训练预算比较**，不是统一端到端成本比较。[AR04]

<a id="s21-7-2"></a>

#### 21.7.2 代表性结果（作者仓库列出的均值 ± 标准差，3 seeds；越低越好）

| 方法 | 方法类别 | Best `val_bpb` | OOM 率 | 严格可得出的结论 |
|---|---|---:|---:|---|
| Centaur + Claude Opus 4.6 | 混合优化 | **0.9739 ± 0.0012** | 17% | 该设置中报告的最佳结果 |
| Centaur + Qwen 27B | 混合优化 | **0.9763 ± 0.0005** | 15% | 经典内部状态 + LLM 建议有效 |
| Centaur + Qwen 0.8B | 混合优化 | **0.9766 ± 0.0008** | 13% | 小模型在受控数值状态辅助下亦可发挥作用 |
| TPE | 经典 HPO | **0.9768 ± 0.0019** | 11% | 固定空间中强且高效的经典基线 |
| Karpathy Agent (Code) + Opus 4.6 | LLM 代码修改 | **0.9770 ± 0.0027** | 5% | 强模型的直接代码编辑接近强经典方法 |
| SMAC | 经典 HPO | 0.9778 ± 0.0020 | 36% | 本实验 OOM 较高，不代表 SMAC 普遍如此 |
| CMA-ES | 经典 HPO | 0.9785 ± 0.0036 | 16% | 混合方法可以优于独立 CMA-ES |
| Karpathy Agent (Code) + Qwen 27B | LLM 代码修改 | 0.9814 ± 0.0046 | 12% | 开放代码编辑能力依赖模型规模 |
| LLAMBO (Paper) + Qwen 27B | LLM HPO | 0.9862 ± 0.0041 | 48% | 数值状态及 OOM 约束跟踪是弱点 |
| Random | 随机搜索 | 0.9873 ± 0.0021 | 56% | 显式约束很重要 |
| LLM 直接给 14 HP + Qwen 27B | 固定空间 LLM | 0.9904 ± 0.0002 | 1% | 少出 OOM 并不自动等于全局最优 |

完整结果还含其他模型与 LLAMBO 实现变体，详见作者 README。[AR04] 表中 `OOM%` 是该文定义的实验 OOM 统计，不能脱离硬件、上限和搜索空间外推到其他任务。

<a id="s21-7-3"></a>

#### 21.7.3 这项研究说明什么、不说明什么

**有证据支持**：在这套**固定的 14 维 HP 空间**中，传统优化器整体优于纯 LLM 数值搜索；而允许 LLM 直接编辑程序能够扩大能力边界，强 LLM 的差距缩小；混合 CMA-ES + LLM 在该实验中达到最优或极具竞争力结果。[AR03]

**仍不能推出**：

1. “LLM 永远不如 HPO”：研究对象、任务长度、预算、空间、模型与提示方法都有限定。
2. “autoresearch 已经全面超越 AutoML”：直接改代码组与固定 HP 组**不在严格同一个搜索空间**，且最终评价仍是特定训练任务的指标。
3. “混合方案总更便宜”：作者没有把 API tokens、Agent 控制/报错时间等全部计入一致的真实总成本。
4. “0.9739 意味广泛领域 SOTA”：数值仅是当前论文实验环境中的 `val_bpb`，不能与不同 tokenizer、硬件和评估设置的结果混排。
5. “LLM 负责大部分候选更好”：作者对 Centaur 的消融反而报告了**过高 LLM 建议比例会损害表现**，说明把强数学搜索器保留为主要探索者往往更稳。[AR04]

**本报告的工程推断**：Agent 负责识别、提出或重构“什么值得优化”，经典优化器负责在约束清晰的连续/离散空间中“怎样高效优化”。在实践中让 Agent 为每一次 learning rate 建议都发一次昂贵大模型请求，可能是错误的职责划分。

### 21.11 autoresearch 的六个系统设计优点与八项隐患

**六个优点（本文分析）**：

1. **只有一个可编辑主文件**：减小 Agent 迷航和 patch 审查范围。
2. **保留不可编辑评测入口**：降低“Agent 自改考卷”的直接风险。
3. **固定每次训练预算**：把算力当作一等公民，便于快速自适应迭代。
4. **Git + TSV**：能追溯“哪个变更导致哪个观测值”。
5. **允许失败也记录**：为 debug 经验、负样本训练与探索策略提供信息。
6. **极小协议开销**：理解、移植到新项目和构建 baseline 都相对容易。

**八项局限与工程风险**：

1. **单一开发验证指标的自适应过拟合**；应有秘密 holdout 和研究结论冻结阶段。
2. **短时预算与长程目标错位**；必须做超预算长度验证。
3. **结果缺乏统计不确定性估计**；小差距需要多 seed/置信区间。
4. **代码 patch 的正确性与供应链风险**；不能仅凭 LLM 自觉不改评测器。
5. **无限运行的资源失控**；硬性 GPU-hour、token、成本和时间上限不可缺。
6. **Git rollback 不等于状态全恢复**；外部数据、缓存、环境变量、依赖镜像和随机状态也应可追踪。
7. **局部连续改进造成探索同质化**；应有多分支、多样性和新颖性配额。
8. **在固定硬件上优化出的技巧可能脆弱**；需要跨设备/精度/驱动重新验证。

原始 README 的快速试验建议包括放宽编码 Agent 的执行权限，**企业或联网环境不应照搬**。采用非 root、无外网/受控出网、私密凭据隔离、只读挂载 `prepare.py` 和评分脚本、磁盘与显存限额、静态扫描和执行超时更为妥当。`program.md` 属于软策略；文件系统权限和独立 Evaluator 才是硬边界。
