### 21.12 如何判断三个方向适合自己的任务？三个完整情景

#### 情景 A：企业的二分类风控表格数据

**目标**：在两小时内取得稳定 AUC、满足解释要求和推理 SLA，并定期重训。

- 适合优先：AutoGluon / FLAML / auto-sklearn 类强 AutoML baseline，配正确时间/实体分割，做成本—准确率 Pareto 比较。
- Agent for AutoML 价值：解释业务意图、检查时间穿越与目标泄漏、选择验证契约、审阅数据异常、修 pipeline 错误、生成受控报告。
- 原版 autoresearch 是否可直接套用：**不推荐直接用**；其训练脚本与 `val_bpb` 指标均与风控任务不同。可**移植实验闭环思想**到受限的表格流水线代码，但必须替换数据/任务/评测契约。
- 风险：Agent 自行修改标签、CV 分割或选最有利测试集，所得收益完全无效。

**结论**：**AutoML 为主、Agent 做治理与编排**，不需要为自主改代码而放弃成熟优化器。

#### 情景 B：新型 Transformer 优化器/注意力机制的短预算验证

**目标**：探索对小语言模型真实训练效率有用的新代码级技巧。

- 适合优先：Karpathy autoresearch 风格，固定训练时长/数据/评测器，Agent 允许改训练实现。
- 加强项：将假设描述、预期机制、对照变更、失败原因结构化记录；每个有价值发现做 3–5 个 seed 的复核（此为建议值，不是原项目默认）；多 budget 外推。
- HPO 的位置：每当产生新架构，先让 TPE/SMAC 在允许的配置空间做有限调参，再与旧架构做公平的 HPO-adjusted 比较，避免把“新架构有更多调参运气”错认成创新。
- 风险：只因短时 loss 更低便宣称更好的 Scaling Law 或大模型新结构。

**结论**：**autoresearch 风格更自然，但需要 AutoML 内核做公平调参与验证**。

#### 情景 C：工业级推荐模型/长时分布式训练

**目标**：多团队、多 GPU、跨日迭代优化，要求失败可恢复且符合治理审计。

- 适合优先：多层编排型 Agent for AutoML / AutoResearch，参考 Auto-RecSys 的异步多服务器实验调度与持久记忆。[AR10]
- 内层：Ray Tune/Optuna/SMAC/ASHA/平台内置 HPO 调参及早停。
- 外层：Agent 提出研究假设、分配探索方向、总结日志；Deterministic Scheduler 执行与重试；独立 Evaluation Service 验收。
- 风险：若把原版“不停运行”“只靠 Git 回滚”的规则移植到跨集群系统，容易出现爆炸性的成本、缓存不一致和环境漂移。

**结论**：融合式系统最合适，核心挑战首先是**长周期可靠性**，其次才是 Agent 的文本推理能力。

### 21.13 推荐混合式架构：AutoML 内核 + Research Agent + 可信实验平台

                                   │
                     [1] Task & Research Contract
                       数据、指标、预算、权限、停止条件
                                   │
           ┌───────────────────────┴────────────────────────┐
           │                                                │
   [2] Research Planner                              [3] Data/Code Profiler
   LLM：假设、代码候选、策略                          schema、依赖、历史实验、显存预测
           │                                                │
           └───────────────────────┬────────────────────────┘

                                   ▼

                        配额、并发、超时、容器隔离

<a id="s21-13-1"></a>

#### 21.13.1 三层控制建议

- **L1 数值层**：TPE/SMAC/CMA-ES 在有效数值空间做高频候选采样，缓存优化器状态；不必每 trial 都触发 LLM。
- **L2 程序层**：Agent 在低频时修改代码结构、提出新特征、修运行逻辑；每次 patch 必须经过 lint、unit tests、权限检查、资源预测。
- **L3 研究层**：Agent 明确“假设是什么、什么实验会推翻它、什么是替代解释”；Evaluator 负责独立证伪/验收。研究层不能直接写入 holdout 指标。

<a id="s21-13-2"></a>

#### 21.13.2 推荐的 Agent action schema（设计示例）

```json
{
  "experiment_id": "run-042",
  "parent_commit": "abcdef1",
  "hypothesis": "A local attention change may increase useful tokens/sec at fixed VRAM",
  "action_type": "code_patch",
  "editable_files": ["train.py"],
  "metric": "val_bpb",
  "metric_direction": "min",
  "training_seconds": 300,
  "resource_caps": {"gpu_count": 1, "max_vram_gb": 76},
  "expected_failure_modes": ["OOM", "divergence", "slower_throughput"],
  "controls": ["same_validation_set", "same_random_seed_for_screening"],
  "decision_after_run": "candidate_for_confirmatory_test"
}
```

**注意**：这是本报告提出的 schema，不是原始仓库提供的 JSON 接口。筛选阶段固定一个 seed 有利于节省噪声，但确认阶段必须换多个 seed，避免对单次偶然结果下注。

### 21.18 最终综合判断与技术选型原则

从**算法层**看：AutoML 在**明确、结构化且可量化**的配置空间内有持续优势；纯 LLM 不擅长精确追踪高维数值搜索状态，并不意味着没有价值。[AR03][AR04]

从**系统层**看：Agent for AutoML 承担**任务理解、规划、工具编排、异常诊断与交付治理**；只有把独立评测、权限控制、成本约束和结构化实验记忆建立起来，系统自动化才会变成稳定能力。[AR06][AR07][AR11]

从**研究方法层**看：Karpathy 原版 autoresearch 把研究缩成一个可亲手检查的协议——**人定义规则和可信评估，Agent 修改代码，真实执行产生反馈，版本控制留存证据**。它是非常好的自主研究教学/原型系统，但**不是研究创造力、普适性与科学真实性的充分保证**。[AR01][AR02][AR09]

从**2026 的趋势**看：前沿问题已从“能否让 Agent 不停地自动跑实验”转向“**如何避免浪费实验、将失败转成共享约束、判断高价值科学进展、在有限 GPU 预算下培养更好的研究策略、在多天多节点环境保证可恢复和可信验收**”。[AR07]–[AR10]

**用一句话定位三者**：**AutoML 把“模型配置优化”变成可计算问题；Agent for AutoML 把“做机器学习”变成可执行的工具计划；autoresearch 把“改进训练方法”变成由真实实验驱动、可持续迭代的程序搜索过程。最值得建设的系统是三者的组合，而不是让 LLM 把它们全部取代。**
