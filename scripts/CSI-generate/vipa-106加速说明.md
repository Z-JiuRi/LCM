## 3. 推荐并行结构

- 每张选定GPU一个常驻spawn进程，利用 `CUDA_VISIBLE_DEVICES` 在导入RT库前限制设备可见性。
- 每个进程内一次只处理一个扇区，动态领取后续扇区；保持扇区原索引及 `seed+sector_index` 不变。
- 静态场景在进程内复用；TX/RX仍按原流程增删，异常清理并丢弃脏缓存。
- 不在进程间传递Sionna/Dr.Jit场景对象，不把多个扇区塞到同一源预算中。
- 当前多GPU任务无通信需求，卡间无NVLink不是主要障碍。瓶颈更可能在CPU路径合成、压缩、D2H传输和磁盘。
- 可用 `--cpu-sets 0-11 12-23 24-47` 作为此机器的初始绑核候选；它只限制CPU位置，不代表三个进程各用12/12/24个BLAS线程。若调度器限制CPU，必须遵守分配范围。
- 线程环境建议从OMP/MKL/OpenBLAS各1线程起，避免每进程96线程争抢；本脚本未覆盖用户已显式设置的环境变量。只有后续CPU计时证明合成占主导才试2/4线程，不无条件开满。

GPU UUID绑定比编号稳妥。实测三卡UUID：

```text
GPU0 GPU-5d1618d3-adcb-2482-c062-f270ca0be78b
GPU1 GPU-1b04d1cb-0924-b10a-ce3b-a0a1b21ca19e
GPU2 GPU-8bbb2909-0d95-c433-7111-2a0914adbb61
```

若作业已有 `CUDA_VISIBLE_DEVICES`，`--gpus`必须使用其中相同标识；不越过调度器分配，不把物理编号和重新编号后的逻辑设备混用。实际GPU-PID绑定仍需在空闲窗口验收，本轮没有创建CUDA上下文。

## 4. 磁盘比GPU更早限制全城规模

默认complex64 `[U,1,32,64]`，每UE每扇区16 KiB。

| 城市 | UE数 | 扇区 | 仅全部扇区CFR | 已知输出容量估算（不含原始路径） |
|---|---:|---:|---:|---:|
| 1km | 29,726 | 18 | 8.16 GiB | 约9.09 GiB |
| 2km | 114,688 | 69 | 120.75 GiB | 约124.40 GiB |
| 4km | 449,988 | 216 | 1483.11 GiB | 约1498.40 GiB |

估算包括服务信道、有效样本全保留时的学习数组及分数/sidecar开销；实际无效UE会使部分学习输出变小，原始路径和容器文件开销又会额外增加。它不是所有输出的严格上界，也不是保证可运行的承诺。

**当前空闲610 GiB的NFS不能容纳4km全扇区CFR，更不用说原始路径。**把文件由压缩改为stored只会增加部分输出大小；不能消除CFR本身的1.45TiB。

建议先申请容量足够、性能明确的scratch/SSD输出目录。不要自行格式化未挂载设备，不直接向接近满的NFS提交全城。小规模/1km验证可按预算使用现有盘，但要估算原始路径。

如果后续同意改变存储契约，可设计两阶段“全扇区仅统计关联，选中后重追踪并仅保存服务信道”，或按UE块处理所有扇区后仅保留服务结果；这不等于删减物理机制，但增加RT或改变遍历/保存流程，需要一致性验证，**本次没有擅自实施或删除全扇区输出**。

## 5. 本轮已实现的加速

实现位于[生成器](<generate_city_csi.py>)：

1. `--gpus`每卡独立常驻进程、动态扇区调度；`--cpu-sets`可选亲和性。
2. 进程内缓存静态场景，避免每扇区重新加载和构建全部网格。
3. `--async-write`有界单批后台写出；`--raw-compression stored`可关闭ZIP压缩CPU成本但不删除任何数组。
4. `--flush-batches`减少每批mmap同步写；扇区结束总会flush。
5. 父进程按扇区流式关联，分数磁盘映射；只保留O(U)选中状态，而非全扇区统计常驻内存。
6. 路径统计按128条分块提升到complex128，减少临时内存。
7. `--export-chunk`只控制CPU后处理工作集；不改变RT `--chunk`。
8. 容量预估和输出盘预检、阶段计时、PID/GPU mask/CPU affinity与场景复用记录。

不是一切都已GPU化：当前 `np.asarray` 将数据移回主机，路径统计、CFR叠加、归一化及NPZ压缩依然是CPU工作。直接换成原生 `paths.cfr()`会改变当前系数定义，不能当作纯性能重构。以后若端口到GPU，需要保持明确的数值契约并与CPU结果对照。

## 6. 推荐命令（未来GPU空闲、环境和容量就绪后）

以下不是本次执行记录，也不代表建议在当前被占用GPU上运行。路径从仓库根执行；几何需先准备，输出目录必须不存在。

```sh
conda activate lcm
export OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 NUMEXPR_NUM_THREADS=1

# CPU几何导出，无RT；默认1km，也可显式指定2/4km源场景与输出。
python scripts/CSI-generate/city_geometry.py --spacing 5

# 配置/容量检查，不导入RT、不触碰GPU。
python scripts/CSI-generate/generate_city_csi.py \
  --gpus 0 1 2 --cpu-sets 0-11 12-23 24-47 \
  --chunk 32 --async-write --raw-compression compressed --dry-run

# 仅在确认环境/空闲资源/输出容量之后运行；先使用受限测试规模。
python scripts/CSI-generate/generate_city_csi.py \
  --gpus 0 1 2 --cpu-sets 0-11 12-23 24-47 \
  --limit-sectors 3 --limit-ues 16 --chunk 8 \
  --async-write --raw-compression compressed \
  --output data/csi/cuda-smoke
```

生产初始RT chunk仍建议32，不因48GB显存就直接改256。候选容量对同一批RX共享，chunk/seed/顺序可能影响路径集合；测试64/128应同时检查结果，而不是只看每秒UE。默认100000样本、深度3不是本轮认可的最终高保真模型；本轮保留这些值只是为了把性能修改与物理升级分开。

如果盘吞吐足够且压缩时间明显高，再比较 `stored`＋异步写；当前盘近满时默认 `compressed` 更稳妥。合理初始配置不等于已测最快，本次没有给出虚构倍数或运行时长。

## 7. 仍须注意的科学与工程边界

- 当前原始系数兼容表示尚未升级为已验证物理基带主输出。
- 绕射拓扑、跨材料楔边、材料频率、植被与透射仍有前述审计问题；多GPU不能修正模型。
- 原始路径保存可能很大，运行中仍可能耗尽空间；启动预检不能预知实际路径数。
- 异步队列有界不是断点续跑；GPU任务失败后会等已运行任务退出，缓存会清理，不提供进程强杀/自动恢复。
- 同GPU不同驱动/不同设备之间的确定性不由固定seed自动保证，应做实际后端对照。
- 当前3卡只能并行扇区任务，吞吐提升受CPU与磁盘限制，不能承诺3倍。
