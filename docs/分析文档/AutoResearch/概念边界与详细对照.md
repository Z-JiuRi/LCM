## 21. 专题增补：AutoML、Agent for AutoML 与 autoresearch 的异同、交叉与融合（2026 年 10 月）

> **2026-10-22 勘误与范围说明：**本章某些关于 `autoresearch` 的论述以 Karpathy 初版的局部自动实验闭环为样本，不应视为所有 autoresearch 系统的上限。请配合新增[第 22 章](生态谱系与项目分组.md#s22)阅读；其中涵盖通用优化、统计评估、复杂科研工作流、多 Agent 协作、自我改进和科研可信性评价，并在新的维度上修正本章的三者比较。

> **增补日期与范围**：2026-10-21。这里的 **`autoresearch`（小写）首先特指 Andrej Karpathy 于 2026 年 3 月公开的同名 GitHub 项目**；**AutoResearch / autonomous research（宽泛意义）** 则指自动提出研究想法、修改研究代码、运行实验、解释结果的研究智能体范式。两者不能混同。另有其他研究者开发的同名 AutoResearch 工具，本文不将其特性错误地归属给 Karpathy 的原始仓库。  
> **证据分级**：标注「**原始项目**」为代码/README/`program.md` 明确说明；标注「**论文实验**」为作者实验报告且未由本报告独立复现；标注「**本文分析/建议**」为系统性归纳与工程设计。对应原文链接见本章末尾 [AR01]–[AR15]。

<a id="s21-1"></a>

### 21.1 一页读懂：三者到底是什么关系？

**高度概括**：

- **AutoML** 是“**让机器自动选择和训练模型**”的研究与工程领域，涵盖数据预处理、特征工程、算法选择、超参数优化（HPO）、神经架构搜索（NAS）、集成与部署前的部分处理，**不能简单等同于 HPO**。它的代表性机制是：在明确定义的问题、约束、搜索空间与评测器下，高效地搜索优良 ML 方案。[R01]–[R12]
- **Agent for AutoML** 是“**让具备规划、工具执行和反馈能力的智能体组织 AutoML 工作**”的系统路线。它可能从自然语言和数据分析开始，决定验证方式、建模流程、调用哪个优化器、如何修复报错、何时停止、怎样交付模型；既可以只调用 AutoML 工具，也可以生成、修改代码。此概念与既有 AutoML **重叠而非取代**。[AR05][AR06]
- **autoresearch（Karpathy 原版）** 是一个极简、限定任务的**自主实验闭环**：人通过 `program.md` 规定研究目标和边界，Agent 仅修改 `train.py`，在固定每次约五分钟的训练预算下运行模型，以 `val_bpb`（越低越好）判断是否保留修改，使用 Git 和 `results.tsv` 留下轨迹，并持续迭代。它更像**Agentic AutoML 与自动化实验研究的交集中的一个具体、可读的研究样机**，**不是**包含科学发现全部步骤的通用科研系统。[AR01][AR02]

因此，三者并不构成“AutoML → Agent for AutoML → autoresearch 的唯一线性演化”。更贴切的是：**AutoML 是问题域与算法工具箱；Agent for AutoML 是组织该问题域任务的一种智能体实现方式；autoresearch 是强调“编辑研究实现 + 真实实验反馈 + 结果选择”的特定架构与文化实践**。若按集合关系理解，Karpathy 的项目位于“LLM 代码代理 × ML 实验优化 × 有约束研究自动化”的交叉点；它当然使用自动 ML 优化思想，但并非所有 AutoML 都是 Agent，也并非所有 autoresearch 都为寻找最优预测模型服务。

<a id="s21-1-1"></a>

#### 21.1.1 最精炼的概念图

```text
                   机器学习 / AI 研发活动
                             │
         ┌───────────────────┼────────────────────┐
         ▼                   ▼                    ▼
  AutoML：自动模型搜索   ML Engineering Agent    Autonomous Research
  CASH/HPO/NAS/集成      规划/编码/调试/评测        假设/试验/证据/迭代
         │                   │                    │
         └───────────────┬───┴────────────────────┘
                         ▼
           Agent for AutoML（交叉领域）
             Agent 编排模型与数据流程
                ┌────────┴────────┐
                ▼                 ▼
        调用经典 AutoML 内核    直接改代码/工作流
                                  │
                                  ▼
               Karpathy autoresearch：极简固定目标
              `program.md` → `train.py` → 五分钟训练
                            → 验证 → 保留/回滚
```

这里的图是**概念关系**而非严格数学集合图；AutoML 也包括传统算法之外的非 HPO 自动化方法，自动化研究也可用于非 ML 领域。

### 21.2 三者在“优化什么”上的本质差异

为了避免术语混淆，先区分四种不同对象：

1. **模型参数** $w$：训练过程中通过 SGD/Muon/AdamW 等优化的权重，不是 AutoML Agent 每一步亲自逐个调节的对象。
2. **配置与流水线** $x$：模型类别、预处理选择、网络深度、学习率、批量大小、集成规则、特征变换等，可由传统 AutoML 搜索。
3. **程序实现** $c$：模型的源代码及训练逻辑。改变它不仅改变超参数，还可能改变优化算法、计算图、架构归纳偏置和执行效率。
4. **研究假设/实验设计** $h$：为何某个机制可能有效、验证它需要什么对照与证据，超出了单次模型调参。

**传统 AutoML 的经典抽象**（是局部代表，而非完整定义）：

$$
\min_{x\in\mathcal S}\,\widehat{L}_{val}(Train(D_{train};x))
\quad\text{s.t.}\quad Cost(x)\leq B,\; Constraints(x)=true.
$$

这里 $\mathcal S$ 一般可由流水线语法、条件型超参数、搜索表或 NAS 超网表示；优化器本身可能是 BO、SMAC、TPE、ASHA、遗传算法或学习到的策略。$\hat L_{\mathrm{val}}$ 是某一验证协议下的估计，并不等于真实部署泛化误差。

**Agent for AutoML 的策略抽象**：

$$
 a_t\sim\pi_{\theta}(a\mid s_t,H_t,K_t),\qquad
 s_{t+1}=\mathrm{Tools}(s_t,a_t),\qquad
 \max_{\pi}\;\mathbb E\big[U(Artifact_T)-\lambda Cost_{total}\big].
$$

状态 $s$ 可包括任务规范、DataProfile、实验仓库、工具和预算；行动 $a$ 可以是“运行 AutoGluon”、 “检测标签泄漏”、 “改验证切分”、 “让 SMAC 提议配置”、 “修复 OOM”或“生成最终产物”。其动作空间比固定 HPO 更异质，但也更难保证动作合法和实验可比。

**autoresearch 原版的抽象**：

$$
 c_{t+1}=Edit_{LLM}(c_t,H_t,program.md),\quad
 y_{t+1}=Eval_{5min}(c_{t+1};\mathrm{fixed\ harness}),
$$

$$
 c^*_{t+1}=\begin{cases}
 c_{t+1},&\text{若通过执行且按规则值得保留},\\
 c^*_t,&\text{否则丢弃/回滚}.
 \end{cases}
$$

这更接近**在代码空间中进行受约束的迭代式黑箱优化**。原版 `program.md` 还考虑显存和“同等效果优先更简单实现”的准则，因此不能将其真实决策规则简化为只看 `val_bpb` 的绝对贪心。其“研究”主要发生在**机器学习训练程序如何改进**这一问题里，项目本身没有自动做文献检索、科研选题审查、统计学复现或论文同行评审等完整步骤。[AR02]

### 21.3 十七个维度的详细对照表

| 对照维度 | 传统 AutoML（典型） | Agent for AutoML（典型） | Karpathy 原版 autoresearch | 解释与边界 |
|---|---|---|---|---|
| 主要目标 | 获得高质量的 ML 模型/流水线 | 自动完成更大范围的 ML 任务 | 改进单 GPU 小语言模型短时训练表现 | 不是互斥的分类 |
| 输入起点 | 数据 + 目标 + 搜索预算 | 自然语言任务、数据与工具上下文 | 既有代码库 + `program.md` | 原版假定任务已明确 |
| 任务边界 | 预先确定或半确定 | 可根据任务动态规划 | `train.py` 可写、`prepare.py` 不可写 | 受限范围恰是项目优点 |
| 搜索对象 | 算法/流水线/HP/架构 | 动作计划 + 工具 + 配置 + 代码 | `train.py` 的架构、优化器、训练逻辑及 HP | “代码搜索”不是 autoresearch 独有 |
| 结构化搜索空间 | 通常是核心 | 可固定、可由 Agent 构造或扩展 | 无固定显式 HP 列表，但受文件/API/依赖限制 | “开放”不等于无限制 |
| 搜索策略 | BO/TPE/SMAC/ASHA/进化等 | LLM 规划、树搜索、搜索器调用、记忆 | Agent 迭代修改、执行、择优保留/回滚 | 原版没有内置数学 BO 内核 |
| 是否必须 LLM | **否** | 多数近期实现使用，概念上非必须 | 原始项目为 LLM/编码 Agent 而设计 | LLM 不是 AutoML 定义要素 |
| 是否必须改代码 | **否** | 否，但可改 | **是**，其主要动作是改 `train.py` | 代码级变化拓宽候选空间 |
| 多 Agent | 非必要 | 可选，常被强调 | 原始 `program.md` 是单 Agent 基础版 | README 对多 Agent 是展望不是默认功能 |
| 实验反馈 | 指标、CV、早停、代理模型 | 指标、错误、运行状态、工具观察 | `val_bpb`、崩溃、显存、训练摘要 | 反馈精度影响自动探索 |
| 实验长度 | 几秒至数天不等 | 依任务/调度变化 | 每次训练固定约 5 分钟，启动/编译额外 | 不是整轮 Agent 工作严格等于 5 分钟 |
| 度量优化方向 | 任务定义，可多目标 | 任务定义，常带安全/成本约束 | `val_bpb` 越低越好，兼顾简单和显存 | 单指标易带来 Goodhart 风险 |
| 记忆与记录 | trial DB/优化器状态 | 长短期记忆、轨迹、检索、artifact | Git commits + `results.tsv` + agent 上下文 | Git 轨迹不等于科学证据完整链 |
| 失败处理 | trial failed、约束惩罚、重采样 | 分析日志、修代码、改变方案 | 报错修复或失败日志并回滚 | 代理若重复同类错误会浪费算力 |
| 终止条件 | 预算/早停/目标达到 | 预算、验收、人工审批、停止策略 | `program.md` 指示运行直到人停止 | 生产上应增加硬性总预算 |
| 最终产物 | 模型/流水线/预测器 | 模型 + 代码 + 报告/部署工件 | 改进后的 `train.py` / Git 分支 / 结果表 | 原版不是端到端部署系统 |
| 主要风险 | 验证过拟合、计算浪费、偏置 | 幻觉、越权、泄漏、不可复现 | 代码修改失控、评测诱导、单目标过拟合 | 共享风险多于标签展示出的差异 |

**关键提醒**：不应把左列偷换成“只能调几个 HP”，也不应把第三列夸成“已自动发现新科学定律”。AutoML 的自动特征构造与 NAS 早已有开放的结构搜索；Agent for AutoML 也早有代码修改、实验迭代与搜索树。autoresearch 的突出价值不是首次发明所有组件，而是**把控制变量、真实 GPU 反馈、Agent 可编辑源码和极简 Git 循环组合成便于理解、复刻和改造的研究协议**。[AR01][AR05][AR06]

### 21.4 从“搜索空间”切入：为什么这是一条真正的技术分界？

<a id="s21-4-1"></a>

#### 21.4.1 传统 AutoML：搜索空间通常先于搜索定义

例如，为表格二分类配置：

```yaml
pipeline:
  imputer: [mean, median, iterative]
  encoder: [onehot, target]
  estimator: [lightgbm, xgboost, random_forest]
  validation: group_5fold
  metric: roc_auc
hpo:
  learning_rate: [0.005, 0.20]  # log-scale
  max_depth: [3, 12]
  num_leaves: [16, 256]
  budget_minutes: 120
```

该空间可包含条件依赖和离散算法选择，搜索并不简单，但**目标空间可形式化、trial 可结构化比较、优化器可以利用显式状态**。它的强项是受控效率和可复现性；代价是“预先没写入的想法”通常无法被发现。

<a id="s21-4-2"></a>

#### 21.4.2 Agent for AutoML：有两层搜索

**外层（策略/规划搜索）**：分析数据、选验证方式、选算法族、是否启用 AutoGluon/FLAML/Optuna、是否进行实验设计。  
**内层（配置/实验搜索）**：自动 HPO、模型训练、交叉验证、集成。  

因此 Agent 可能选择“修改搜索空间”而非“在原搜索空间内采样”。例如发现训练标签随时间泄漏后，将随机分割改为时间分割，虽然短期分数下降，却令估计更可信。反之它可能错误地更改切分并使自己的指标虚增，所以验证契约必须独立于 Agent。

<a id="s21-4-3"></a>

#### 21.4.3 autoresearch：把程序本身作为候选

Agent 可以不只是给出 `learning_rate=0.02`，而是改变 `train.py` 中的注意力方式、归一化实现、参数化、权重衰减逻辑、优化器细节、批量策略、训练效率。这种表达能力显著更强，却有三个计算机科学代价：

- **候选未必可执行**：语法错误、形状冲突、OOM、NaN、依赖缺失都变成候选的一部分。
- **候选不可自然数值化**：两个代码 patch 的距离很难像学习率之间的距离一样定义，传统 BO 代理难以直接套用。
- **局部单分支搜索可能早熟收敛**：若每次只沿当前最好代码版本修改并舍弃失败分支，复杂的“先退一步再跃迁”的设计不容易保留。多分支树搜索能缓解，却又引入昂贵的分支管理与 GPU 调度。[AR05][AR07]

**本文分析**：有意义的区分不是“自动化程度越高越先进”，而是 **参数化、代码编辑、研究假设** 三类候选表示之间的取舍。在已知空间中，数学优化器拥有优越的状态表示；在未知空间中，LLM 的代码先验和语义知识能够提出新候选，但其数值记忆/约束处理未必优于传统优化器。

<a id="s21-6"></a>

### 21.6 三者的“智能”分布在哪里？

一个容易误解的说法是“AutoML 没有智能、Agent 有智能”。实际上传统 AutoML 中的**贝叶斯优化代理模型、元学习 warm-start、强化学习 NAS/控制器、贝叶斯集成策略**都可承载自适应与学习。区别不是有无智能，而是**策略表示方式与动作粒度**。

| 策略来源 | 传统 AutoML | Agent for AutoML | autoresearch 原版 |
|---|---|---|---|
| 数据统计与 surrogate | BO/SMAC/TPE 等显式建模 | 可调用并融合 | 默认不内置此类状态模型 |
| 语义与研究知识 | 由专家设计搜索空间、元特征 | LLM 从任务与经验提取 | LLM 阅读代码与日志后生成 patch |
| 长期经验 | 元学习库、历史 trial | 轨迹记忆、RAG、经验技能 | Git 历史/TSV/上下文，可扩展 |
| 控制规则 | 算法/预算调度 | Policy、权限、规划策略 | 人写 `program.md` |
| 动作合法性 | 大多由搜索空间结构保证 | 需工具约束与验证门禁 | 单文件可编辑 + 禁改评测器 |

**重要结论**：原版 autoresearch 的**控制平面本身就是 Prompt/Skill**。人编辑 `program.md`，Agent 编辑 `train.py`；这相当于把研究 SOP（标准作业程序）显式写成了一段可执行的自然语言政策。但 prompt 约束只是行为指导，**并不能代替容器级文件权限或不可更改的评估器**，尤其是当 Agent 拥有高权限 shell 时。
